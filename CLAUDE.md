# LetsClip

An instant replay recorder for one monitor that runs in the background. A WPF window hosts a `BlazorWebView` whose UI is MudBlazor, laid out like `SoTF.Editor`, with `WiFiWatch`'s tray and startup registration. It starts with Windows in the tray and keeps the last 30, 60 or 120 seconds of the chosen monitor (the primary until one is picked) and system audio (optional microphone) in a rolling cache, all the time or only while a game runs (`AFK-Assist`'s `GameScanner`). A hotkey saves them as an MP4 clip of exactly that length, and the clip editor trims it and exports an MP4, under a size limit when one is needed.

| Project | Holds |
|---|---|
| `LetsClip.Data` (`net10.0`) | `Helpers` (`AppInfo`, `Formatter`, `ClipNames`, `SizeBudget`, `TrimRange`, `Hotkey`, `FilePaths`, each with a Debug self test), `ViewModels` (records the UI and services share), `Enums` (`CaptureHolds` among them) |
| `LetsClip.Services` (`net10.0-windows`) | `Capture` (`ReplayRecorder` state and saves, `CaptureSession` the two FFmpeg processes, `AudioMixer` WASAPI onto the media clock, `SegmentCache`, `ClipSaver`, `MonitorCatalog` DXGI, display config and refresh rates, `AudioDevices`, `CacheFolders`, `CaptureController` the app's one entry point, its automatic buffering and the games list), `Games` (`GameScanner` copied from `AFK-Assist`, `GameWatcher`), `Integration` (`StartupRegistration` copied from `WiFiWatch`, `Updater`), `Media` (`FFmpeg` process runner with a kill-on-close job, `MediaProbe`, `VideoEncoders`, `ClipLibrary`, `ClipExporter`), `Storage` (`UserSettings`) |
| `LetsClip.Desktop` (`net10.0-windows10.0.17763.0`) | `App` (startup, `--tray`, logging, single instance, lock, sleep and display events), `MainWindow` (WebView2 host, tray, close to tray, virtual hosts), `Interop` (`DesktopShell` for the page, `MonitorOverlay`, `WindowMessages` for the hotkey and display power, `TrayMenu`, `TrayBalloon`, `SaveChime`, `Explorer`, `WindowCaptionTheme`), `Components`, `Theming`, `wwwroot`, `FFmpeg` |

Packages: MudBlazor, `Microsoft.AspNetCore.Components.WebView.Wpf`, NAudio.Wasapi 3, NLog. FFmpeg 9.0.2 (BtbN GPL shared build, pinned by SHA-256 in `LetsClip.Desktop/FFmpeg`) does capture, encoding, segmenting, remuxing, probing, thumbnails and export as child processes. No database.

## Build, Run And Publish

The FFmpeg binaries are not in git. After cloning, once:

```bash
powershell -ExecutionPolicy Bypass -File LetsClip.Desktop/FFmpeg/Get-FFmpeg.ps1
```

```bash
dotnet build LetsClip.slnx
```

```bash
dotnet run --project LetsClip.Desktop
```

```bash
dotnet publish LetsClip.Desktop -c Release
```

The publish folder holds only `LetsClip_v<Version>.exe`: `IncludeAllContentForSelfExtract` and the `BundleWebRoot` target pack `wwwroot` and the `FFmpeg` folder inside it, extracted once on first start. The exe is ReadyToRun (`PublishReadyToRun`), so the first page opens sooner. `LetsClip.Desktop` keeps the Windows SDK version in `net10.0-windows10.0.17763.0`: the app itself uses no WinRT, but `BlazorWebView`'s `WebView2CompositionControl` loads `Microsoft.Windows.SDK.NET` when the window loads. Plain `net10.0-windows` built and published 16.5 MB smaller and then failed there with a `FileNotFoundException`, the page never showing (tried in the November 2026 audit). A build without the FFmpeg files stops with a message (`RequireFFmpeg`, before `BeforeBuild`: hooked to `Build` it ran after the copy step, which failed first on the missing `LICENSE.txt`).

`.github/workflows/build.yml` fetches the pinned FFmpeg and builds in Release on `windows-latest` for every push and pull request. Releases are made by hand, the shared way: the exe as the only asset and an empty body, and only once the owner has tried the build left running for them and said publish. A patch number is the owner's pick when asked for (1.1.1); `AppInfo.VersionText` then shows three parts.

A Release exe someone started from `bin\Release` locks that folder; publish to another folder with `-p:BaseOutputPath=<folder>\` rather than stopping it.

## Where Data Lives

| What | Where |
|---|---|
| Settings (`UserSettings`) | `%AppData%\LetsClip\settings.json`, written through a temporary file flushed to disk and a rename |
| Clip metadata (trim, recorded time, frame rate, size, given name, game) | `%AppData%\LetsClip\Clips\<hash of path>.json`, ignored when the file's size or write time no longer match |
| WebView2 profile | `%AppData%\LetsClip\WebView2` |
| Replay cache | `%LocalAppData%\LetsClip\Cache\<session guid>\seg_*.ts` and `aud_*.ts` |
| Thumbnails and timeline strips | `%LocalAppData%\LetsClip\Thumbnails`, deleted with the clip's metadata when the library's watcher sees the clip deleted, in the app or in Explorer |
| Logs | `Documents\LetsClip\Logs`, one file a day at Debug, the newest 30 kept (`maxArchiveFiles`) |
| Saved clips | `Videos\LetsClip` (the Videos known folder) or the folder picked in Settings; the Clips page reloads on every `ClipSaved` and on the folder watcher |
| Exports | `<clips folder>\Exports` |
| Originals of cut clips | `<clips folder>\.Originals\<same file name>`, a hidden folder, removed when its last original is restored; recycling a clip recycles its original too |
| Start with Windows | `HKCU\...\Run` value `LetsClip` with `--tray`, and `Start Menu\Programs\01 Apps\LetsClip.lnk`, both rewritten on every Release launch |

A Debug build uses `LetsClip Debug` for all of these (`AppInfo.FolderName`) and never registers with Windows. `LETSCLIP_ROOT` moves every one of them under a scratch folder, gives the app its own single instance handle and skips the registration, for tests.

## Automatic Recording

- Recording has no switch, the owner's pick (a Buffer in Background switch, a first run notice and a tray pause all came and went): `CaptureController` starts it at launch, after an unlock, a wake, the display coming back and a monitor returning, and only Exit ends it. Every word on screen says Recording, never Buffering: the chip and tray read Recording, Recording Overwatch, Waiting for a Game or App, Saving Clip or Not Recording.
- People set it once and forget it, so every failure retries by itself (`ReplayRecorder.Failed`, `CaptureController.RetryAsync`): 2 s, then 5, 15 and 30 s, then each minute, a failed start and a dropped session alike; the count starts over only when a session had run 30 s, so a capture that starts and dies at once keeps backing off. Any exception a start throws ends on Error and retries, a COM error from a restarting audio service too, never stuck on Starting. A session that ran 30 s or more restarts out of sight: `CaptureController.ShowsError` stays false, so the chip, tray and Save button read Recording, and a press waits for the restart. Only a failure on the retry shows the error, with Try Again for an impatient click, while the retries go on (HDR turned off or space freed starts recording within the minute). Killing the video FFmpeg of a running session restarted it 5 s later with the chip on Recording throughout.
- `CaptureHolds` (locked, asleep, display off, exiting) stop it and clear the history; it starts again only when no hold is left. Displays that sleep after the Windows timeout count, so an app left alone stops recording on its own.
- A saved monitor that is unplugged falls back to the primary, so recording never sits idle without a word; it moves back when the monitor returns. `CaptureController.DisplaysChangedAsync` names what happened to the running monitor (disconnected, or its display settings changed) and restarts only what differs. 30 FPS is always offered, even on a 24 Hz screen.
- A start that throws anything (a blocked FFmpeg, an unwritable cache) ends on Error, never stuck on Starting. An encoder test that fails or hangs past 20 s counts as failed and the next encoder takes over, with the warning naming it; it is tried again at the next start, and only passes are cached (`VideoEncoders.WorksAsync`). AMF sometimes hangs at init right after another AMF process was killed: seen twice in the November 2026 sweep, where a hung test once left the 1440p144 start on Error.
- `ReplayRecorder` raises `StatusChanged` only when the status really changes, and its health check ticks only while a session runs: the tray and an open page no longer wake every second.
- Games Only records the game's own window, never the desktop: alt tab, chats and notifications stay out of the clip. `GameWatcher` scans the running processes every two seconds for a known game with a window on screen (not minimised), so a game started before LetsClip is found too, and counts it until its process exits, read from that one process's handle without listing processes again. It scans only while Games Only is on and nothing holds capture. Games Only can be turned on with no known game, the owner's pick: it then waits for one, Waiting for a Game or App on the chip. Since any app can be added, every word on screen says Games and Apps (the switch reads Games and Apps Only, the capture panel row Game or App, the dialog Games and Apps with Add Game or App); the setting keeps its `GamesOnly` name. Taking the recorded game off the list stops its recording at once (`GameWatcher.SetGames` lets go of it); before, it kept recording until the game exited. Known games are `GameScanner`'s Steam, Epic, Riot, Rockstar and Roblox libraries plus `Games` folders on C, D and E, with `UserSettings.AddedGames` added and `RemovedGames` taken out (`CaptureController.GameList`). Turning Games Only on or off stops the capture and starts the other source.
- Settings → Games and Apps Only → the Edit Games and Apps chip (never a count, the owner's pick) opens `GamesDialog`, an outlined table with no header and no cell borders (a sticky one word header let scrolled rows peek under it): the red X keeps the key in `RemovedGames`, so the game stays greyed at the bottom with Add Back. Add Game is a menu of the apps open right now (`GameWatcher.RunningApps`, Windows' own hosts and WebView2 left out, read when the dialog opens) plus Browse for an Exe; both key the game by `GameScanner.NormalizeProcessKey` of its process and name it by its product name (`GameWatcher.GameOf`).
- Every ask (a setting, the page, the tray, Windows events, the game watcher, a dropped capture) runs `CaptureController.StepAsync` alone under one semaphore: it applies its change, works out the wanted `CaptureOptions` (null while held or with no game) and restarts only when that differs from the running session's `ReplayRecorder.Options`. Nine quick clicks on the capture panel restarted once, with the last values; 40 setting changes from several threads at once ended on one FFmpeg pair and one cache folder with the last values. Settings are written inside the controller's lock, so quick changes land on disk in order.
- A stop for a restart, a hold or exit first lets a running save finish (`WaitForSavesAsync`, 5 s at most), so a clip saved just before a change keeps its whole length. A press while capture starts or restarts is never refused: `CaptureController.SaveAsync` waits for the step (15 s at most) and saves what the new session holds, even a second of it, the owner's pick. Only Games Only with no game, a hold or an error says `Nothing is being recorded right now`.
- Starts and restarts stay out of sight: the chip and the tray read Recording throughout (`CaptureController.IsRecording`, `StatusText`) and the Save button stays enabled, never Starting or Stopping.
- First start defaults (`UserSettings`), the owner's pick: Games Only on, 30 s, 1080p (exports top out at 1080p, so more only costs), 60 FPS, Normal, system audio on, the microphone off with Noise Cancellation on, Start with Windows and Save Sound on, F10 (it takes F10 from every other app while LetsClip runs, Visual Studio's Step Over too, the owner's pick over Ctrl+Shift+F8), Automatic for both audio devices.
- Defaults the owner picks later reach existing users once: `UserSettings.DefaultsVersion` (a file without it predates it, read through `LegacySettings`) below `CurrentDefaults` gets them and is saved at once. Version 1 set F10 and Automatic for both devices. Raise `CurrentDefaults` and add to that block for the next such pick, never reset what people chose without the owner asking.
- The reason a session ended names the exit code.

## Capture

- Monitors: `ddagrab` (Desktop Duplication) on the adapter and output that `MonitorCatalog` finds for the saved monitor's device path, never a stored index. The frame comes back unrotated: rotation 90 is `transpose=clock`, 270 `transpose=cclock`, 180 both flips (checked on the portrait LS27AG500N at 270).
- Game windows: `gfxcapture` (Windows Graphics Capture) on the window handle `GameWatcher.GameWindow` reads fresh at each start, with no yellow border, sized to the window's own shape inside the resolution box of the monitor holding it (`MonitorCatalog.ClientSizeOf`, `ReplayRecorder.FitInside`, never upscaled), so a maximised or windowed app gets no bars; only a window resized mid session is letterboxed (`resize_mode=scale_aspect`). The bars a v1.2 clip showed were that padding, never the desktop around the window. It sends a frame only when the window changes, so keyframes are forced each second of time (`-force_key_frames`), and the video stall check and slow frame rate warning are off for it: a minimised game sends nothing and only its exit ends the session. A window still from its first moment sends one frame, which AMF and x264 both hold (`-latency 1 -async_depth 1` did not release it on AMF, only x264's `zerolatency` did), so no segment ever closes; up to v1.7 such a start failed every encoder after 12 s and retried with an error, which a paused YouTube window hit on 6 November 2026. A window session now counts as started once its audio writes a segment, or at the 12 s timeout while FFmpeg still runs (`CaptureSession.LaunchAsync`), since `VideoEncoders.WorksAsync` already proved the encoder; video flows the moment the window draws, and a save before that says `Nothing has moved in the window yet`. An `overlay` onto a paced `color` source does not help: frame sync waits for the window's next frame too.
- Resolution is a select of `UserSettings.ResolutionChoices` (480p, 720p, 1080p, 1440p, 2160p) below the picked monitor's short side plus the monitor's own size, labelled by that side (`CaptureController.ResolutionChoices`). A choice fits its 16 by 9 box in the monitor's orientation, never up (`ReplayRecorder.OutputSize`, 480p is 854 x 480); one at or above the short side is the monitor's own size. The saved value is the picked lines (`UserSettings.Resolution`, 1080 by default), and a monitor without it takes the nearest below, like frame rates. An old `FullResolution` on becomes 2160. Frame rates are `UserSettings.FrameRateChoices` up to the monitor's refresh rate, which `MonitorCatalog.DisplayDetails` takes from the `QueryDisplayConfig` path's own fraction rounded with `Math.Round` (59.94 Hz reads 60, 143.86 Hz 144, never 59 or a decimal), the owner's pick; every shown rate, log and choice uses that one number. `DEVMODE`'s `dmDisplayFrequency` truncates, so it read 59 on a 59.94 Hz screen.
- `hwdownload`, then one CPU `scale` with BT.709 limited range, then `nv12`. Measured with the window shown: 2560 x 1440 to 1080p at 60 FPS takes about half of one CPU core for the video process, 2560 x 1440 native at 240 FPS about two cores and 606 MB, holding 240 FPS (7198 frames in a 30 s clip).
- Intel Quick Sync converts on the GPU instead (`VideoEncoders.QuickSyncGpu`, `GpuFrames`): `hwmap=derive_device=qsv`, then `vpp_qsv` sizes, turns (`transpose` clock, cclock, reversal) and makes `nv12` with BT.709 limited range. Measured in November 2026 on an i5-1335U with Iris Xe and FFmpeg 9.0.2: Desktop Duplication at 1080p60 takes 21% of a core against 83% on the CPU route, window capture 4.8 against 13.9 ms of CPU per frame, both holding the rate (10,798 frames in 3 minutes with a build running); colour bars score 43.9 dB for the conversion alone (CPU `scale` 42.6) and 48.6 after encoding (45.1), limited range on both. Downscaling 1440p to 1080p is softer (40 to 42 dB against Lanczos in every `scale_mode`, CPU bilinear 44.3), so only a monitor above 1080p recorded at 1080p differs. A failed GPU start falls back to the CPU route on the same encoder without a warning. `scale_d3d11` fails on Iris Xe too (`E_INVALIDARG`); AMD and NVIDIA keep the CPU route, NVENC untested.
- No GPU-only route works on the RX 9070 XT with FFmpeg 9.0.2, all retried in November 2026: D3D11 frames straight into `h264_amf` fail in `SubmitInput` (error 18, DirectX failed), `scale_d3d11` cannot create its NV12 texture (`E_INVALIDARG`), `vpp_amf` fails `AMFConverter-Init` (error 10) whatever its colour options, `hwmap` to AMF is not implemented, Vulkan mapping is not implemented for D3D11, and `vsrc_amf` rejects 240 FPS while its frames fail encoder init at lower rates. Downloaded BGRA fed to AMF halves the CPU at 240 FPS (0.84 cores against 1.70), but AMF's own conversion scored 36.6 dB on colour bars against 44.6 dB for the `scale` above, and its range follows the input's tags (full range from `ddagrab`), so it is not used. `fast_bilinear` saves no CPU per frame and drops to 39.6 dB. Colour checks use known bars, never the live screen, whose frames already differ at 24 dB.
- The encoder is the first that really encodes a few test frames (`VideoEncoders.WorksAsync`): AMF, NVENC or Quick Sync for each GPU vendor present, then x264. A one second GOP, no B frames, and `h264_metadata` writes the BT.709 colour description the hardware encoders leave out. Rates grow with the pixel rate: load is the square root of pixels per second over 1080p60, at least the frame's own share of 1080p (1 from 1080p up, 0.67 at 720p, 0.44 at 480p), the average 20 Mbps and the peak 40 Mbps times the load. Only AMF and x264 are tested on this PC.
- Quality is Normal, High or Max (`CaptureQuality`, Normal by default): High gives 1.75 and Max 2.5 times the average and peak bits, with quality level 22, 19 or 16 for NVENC's CQ, Quick Sync and x264's CRF, and 42, 48 or 51 for AMF's QVBR, which counts up (`VideoEncoders.TuningOf`); the replay cache grows with the peak. Up to v1.2.1 AMF got 22, 19 and 16 too, so Max recorded worse than Normal on AMD: a 1440p clip of a film came out at 1.18 Mbps. The AMF levels are matched to x264 by PSNR on a noisy 1440p60 pattern (AMF 42 32.13 dB at 33 Mbps against CRF 22 32.11 dB at 28 Mbps, AMF 48 32.23 dB against CRF 19 32.25 dB).
- One second MPEG-TS segments from the `segment` muxer, each listed on standard output as `name,start,end`, with `mpegts_copyts=1` so the files keep the media clock. `SegmentCache` keeps the replay length plus three seconds, within 1.5 GB or the replay length at the peak rate plus 20%, whichever is larger, and never evicts past a pinned save.
- Noise Cancellation (`UserSettings.NoiseCancellation`, on by default, always shown under Microphone and disabled while the microphone is off) cleans only the microphone: `AudioMixer` then writes four channels, system audio on the first two and the microphone on the last two, and the audio FFmpeg runs `CaptureSession.MicrophoneCleaning` (`highpass` at 80 Hz, `afftdn` at 12 dB with noise tracking, a gentle `agate`) on those before `amix` puts them back to stereo. On a synthetic voice with pink noise at about -53 dB the gaps fell to -68 dB, the voice was unchanged, and only the first 50 ms of a word lost 3 dB; stronger `afftdn` settings gained nothing, a harder gate cut more but risks quiet speech.
- Audio runs in a second FFmpeg process. In one process the scheduler held the live video back whenever the piped audio lagged the video by 100 ms, and capture fell to 6 FPS; apart, both run free.
- `FFmpeg.Start` opts every child out of power throttling (`SetProcessInformation`, execution speed and timer resolution). Windows throttles the children of an app whose window is shown, even when covered, and capture fell to 35 to 45 FPS whenever the LetsClip window was open; hidden to the tray it was always 60. A sibling FFmpeg started outside LetsClip never slowed, which is how it was found.
- Monitor frames are timed by their count, not by `ddagrab`'s stamp: `ddagrab` stamps each frame with the moment it was grabbed, rounded to the frame grid, so with the CPU busy (a game plus the encoder) a late grab took the next slot and the one after it doubled up, a frame held twice as long. A 30 s Overwatch clip at 1080p60 had 15 of them, a 30 s x264 test 115, and a 240 FPS clip read as jumping and pausing. `setpts` now puts frame N in slot N from the first frame and re-anchors only past 1.5 slots of real drift (`CaptureSession.VideoArguments`); the same load then gave 1803 frames all 16.7 ms apart. Capture alone, idle, was always exact. Window capture keeps its own stamps, since a window sends frames only when it changes, and `-fps_mode vfr` drops a second frame that rounds into a slot already taken: with `passthrough` a 60 FPS window clip of a 240 Hz window held 1873 frames, 73 of them stacked on a used slot, and a 144 FPS one 1108; with `vfr` the 60 FPS clip holds 1800, all 16.7 ms apart. At rates that do not divide the window's own rate, empty slots stay (a 144 FPS clip of a 240 Hz window holds some frames for two slots), as any sampling of it would.
- The media clock: `AudioMixer` places each WASAPI packet at its QPC time (sample zero is the session's start, media time 1.0), silence and gaps stay silence, and a packet within 20 ms of the last one continues it. Video gets onto the same clock with one wall clock reading at its first frame (`setpts` with `RTCTIME`). Both clocks are read in microseconds.
- The audio process shifts its output with `-output_ts_offset`: FFmpeg 9.0.2 ignores `-itsoffset` on the raw `f32le` pipe, which left v1.2's audio on a clock one lead second early, so every clip played its sound about 0.94 s before the picture (measured with a flashing window and a 20 ms WASAPI beep). Since the fix the beep lands 11 to 54 ms after the flash over ten beeps.
- A save pins the cache, waits for the segment holding the key press to close, joins the segments with the `concat:` protocol and stream copies them up to the press into an MP4 named `LetsClip yyyy-MM-dd HH-mm-ss.mp4` (`ClipNames`). Both inputs are shifted so the replay's start is zero (`ClipSaver`, `-itsoffset` minus the start, no `-avoid_negative_ts`); the keyframe pre-roll before it lands below zero, where the MP4 edit list hides it, so a 30 s replay plays, probes and exports as 30 s (30.00 to 30.03 s measured, 900 frames at 30 FPS). WebView2 and FFmpeg both honour it: a clip whose hidden pre-roll is red shows no red frame in the editor, and an export from it matches the source at 44.5 dB against 19 dB half a second off. A session younger than the replay starts at its first sample instead (media time 1.0). It runs off the UI thread and returns before any thumbnail is made (the library makes it later). A monitor save took 1.5 to 2.2 s from press to file on the i5.
- A still game window sends no frames, so its segment never closed and a save waited out its 8 s limit (9 s for a Claude window). Window sessions write their video segments with `flush_packets=1`; after 1.5 s the save joins the open segment (the newest `seg_` file) as it stands on disk, its last frame holding to the press while the audio runs on, shifted to the replay's start with `-itsoffset` when it is older than that. At most the encoder's last few held frames are missing. Measured on the i5: 2.2 s from press to file, for a window still 10 s (moving video, then its last frame) and still 40 s (one frame, 30 s of sound).
- Quick Sync ignored the forced keyframes as split points until `-forced_idr 1` (AMF and NVENC already force IDR): a game window's segments then closed only every 60 encoded frames, or never while still, which is what made that 9 s save.
- A clips folder on a drive that is gone saves to `Videos\LetsClip` instead, so the replay is kept, and the balloon then shows that file in Explorer (folders compare through `FilePaths.AreSame`, case and a trailing slash aside); save errors read as plain words (`ReplayRecorder.SaveErrorOf`). `ClipMetadata.FrameRate` keeps the capture rate, which exports prefer over a window clip's low probed average.
- While a save runs (`CaptureStatus.IsSaving`, from the hotkey, the tray or the button) the Save button's icon is a spinner in the icon's place (`button-spinner` inside a `mud-button-icon-start` span) and a second press does nothing; the chip reads Saving Clip. A save plays `SaveChime` (two soft bell notes a fifth apart, a third of a second whose last 30 ms fade to silence, played by `PlaySoundW` from a pinned buffer so any thread can call it; `SoundPlayer` raced on two quick saves) instead of the Windows sound, when Save Sound is on, the moment the save is accepted (`ReplayRecorder.SaveStarted`), not when the file is written; the balloon still waits for `ClipSaved`; `SaveChime.Play` first has `AudioMixer.MuteSystemAudio` write the loopback as silence for that long, so the chime never lands in the next clip. Its volume is `UserSettings.SaveSoundVolume` (full by default, the owner's pick, 10% to 100% in tenths): `SaveChime` renders one pinned wave per tenth on first use, and Settings sets it with the same `VolumeButton` the editor uses, playing the chime at each new level; a click plays it. The tray balloon is silent: `TrayBalloon` sends `NIIF_NOSOUND` through `Shell_NotifyIconW`, borrowing `NotifyIcon`'s private `_window` and `_id`.
- Lock, sleep, display off, a monitor change and a stalled encoder all end the session and clear its history; nothing splices across them.
- A stall is 20 s without a segment (`ReplayRecorder.s_stallTimeout`; a save still waits 8 s at most, `s_saveTimeout`), and the log names how long each stream was quiet. At 8 s v1.5 failed three times in four minutes on 6 November 2026 on the i5: the stopped sessions' cache folders showed both FFmpeg processes stopping together and starting their next segment in the same millisecond after 8 to 9 s, so the disk or file system froze under them (the System log had a volume shadow copy aborting on C: just before), not the encoder or the microphone. A 12 minute harness run with the microphone and Noise Cancellation on, same settings, never went past 1.0 s between segments. Such a freeze now passes with the history kept; a real hang retries as above. `CacheFolders.Delete` retries for two seconds, since a killed encoder can hold its last segment that long.

## Export

- Re-encodes the trimmed range from the saved clip at 1080p at most (no resolution choice, the owner's pick): `-ss` before `-i` (frame accurate when transcoding), `scale` plus `pad` to even sizes, `yuv420p`, BT.709 tags, AAC 128 kbps, `faststart`.
- The ceiling is the size past which an export gains nothing (`SizeBudget.CeilingMegabytes`): Sharp twice over at the output size, frame rate and audio (0.09 bits per pixel, a slow clip counted at 30 frames since each of its frames changes more), or half again the selection's share of the source file when that is smaller, never below twice the video floor or 2 MB. A 5.5 MB still clip once offered up to 47 MB; it now needs 9 MB. `ClipExporter` clamps every request to it, capped at 4000 MB, since 4000 MB failed in FFmpeg with Result Too Large.
- Size Limit is a select of fixed limits (`SizeBudget.Limits`, 20, 50, 100, 200 and 500 MB) offered only below the ceiling and where the export can still meet them, then Unlimited (4000 MB, so the ceiling decides) (`SizeBudget.LimitsFor`). With nothing below the ceiling the row is gone and the export aims at the ceiling. The pick is saved as picked (`ExportMegabytes`, 20 MB by default): a saved limit at or above an export's ceiling means Unlimited for it, else the nearest offered below, else the smallest offered. Its info icon says what the limit and Unlimited do, without naming any app.
- The verdict reads Sharp whenever the target holds the selection's own bytes (`keepsSource`), whatever the bits per pixel, since a re-encode cannot find detail its source never had; otherwise the bit rates below decide. The Bitrate row shows the most video gets, since still scenes come out smaller.
- Audio is a `VolumeButton` (mute and a volume slider in tenths, `ExportAudio` and `ExportVolume`, 100% by default) with the level greyed beside it; the export applies it as `-af volume` (`ExportRequest.Volume`, zero leaves the sound out). Output shows `MediaChips`: the resolution class (`Formatter.FormatResolution` by the short side: SD, HD, FHD, QHD, 4K, a window clip slightly under still counts) and the frame rate, the same chips the clip cards show over their thumbnails.
- With a selection shorter than the clip the button reads Export and Save, the owner's pick: after a successful export the clip itself is cut to the selection (`ClipLibrary.CutAsync`, Saving the Cut on the progress). The cut is a stream copy with `-ss` before the input: FFmpeg 9.0.2 starts at the keyframe before and writes the frames up to the in point with negative times and the discard flag, which the MP4 edit list hides, so it is frame exact and lossless (a 3.25 to 10.5 s cut of a 60 FPS clip held exactly 435 frames, its first byte for byte the source's frame at 3.25 s). The first cut moves the full clip to `.Originals`; later cuts only replace the cut. Restore Original (`Restore`, in the editor header while an original exists) moves it back. Both keep the name, game, date and frame rate, clear the trim and the pictures, and reload the editor, whose video URL carries the file's write time so WebView2 never plays the old file from cache. The library forgets a clip's metadata only once its folder settles with the file still gone (`ClipLibrary.Settle`), since a cut moves the file away and back.
- Frame Rate is 60 FPS or the clip's own when it runs above 60 (`ExportFullFrameRate`, `ClipExporter.FrameRateOf`); a 240 FPS clip at 10 MB is otherwise Too Small.
- `SizeBudget` turns the limit (decimal MB) into a video bitrate after a 5% margin, the MP4 index and audio. Bits per pixel decide Sharp, Good, Soft or Too Small; Too Small refuses.
- The hardware encoder goes first (single pass VBR aimed at 90% of the budget, since AMF overshoots), x264 two pass second. A pass whose progress stops for 15 s is killed and counts as a failed encode (`ClipExporter.RunPassAsync`), so a hung AMF export moves on to x264 instead of waiting out the 30 minute limit; one hung that way in the November 2026 sweep. Every result is probed and its real size checked; over the limit retries at a lower bitrate, twice per encoder. An export is named by its clip, never by its limit (`LetsClip 5-11-2026 at 21h10`, then `(2)`). Cancelling mid-encode once reported "Export failed, the file could not be written" and left the partial file: the killed encoder's file stays locked a moment, so `FFmpeg.DeleteOutputAsync` retries for two seconds and never replaces the real outcome. On a 30 second noise heavy 1080p60 test AMF landed 18.4 MB for 20 MB and 9.3 MB for 10 MB on the first try in about 9 s, and scored VMAF 85 against x264 two pass 74 at the same size (28 s). A 12 s 1080p120 test pattern landed 8.7 MB for 10 MB at 60 FPS.

## Updates

`Updater.CheckAsync` reads the `releases/latest` redirect without following it, so it needs no token. It runs on every start (no setting) and from **More (⋮) → Check for Updates**; a newer version opens `UpdateDialog` and a red dot stays until restart: a `MudBadge` on the More menu (`d-flex`, or it lifted the button 2 px), then `update-dot` on Check for Updates. The dialog shows no release notes, since every release body is empty; `AppInfo.ReleaseApiUrl` only feeds the checksum lookup below.

Update Now hides the X and Escape until the download fails (`UpdateDialog.SetClosableAsync`). `Updater.DownloadAsync` saves the new exe beside the running one through a `.download` file that must match the asset's SHA-256 `digest`; a mismatch or missing digest opens the release page instead. `Updater.Launch` starts it with `--after-update <pid>` and the window exits through `MainWindow.ExitAsync`, finishing saves. The new exe runs `Updater.FinishPreviousVersion` before the single-instance check: it waits up to 60 s for the old process (which may finish a save for up to 15 s first) and deletes every other `LetsClip_v*.exe` beside it. A protected folder, a Debug build or a renamed exe (`Updater.CanInstall`) opens the release page. Build with `-p:Version=0.9` to see the dialog.

## Looks Wrong, Is Not

- Each capture writes two segment streams (`seg_` video, `aud_` audio); the save joins them by their shared timestamps.
- `ClipSaver` writes the clip as `.LetsClip-<guid>.mp4` and renames it only after it probes back; such leftovers after a crash are ignored by the library and never deleted, since the clips folder belongs to the user.
- `CacheFolders.Delete` refuses anything but a GUID folder directly under the cache root and only deletes files named like segments or x264 pass logs.
- The preview plays with sound while recording, so its sound lands in the next clip, the owner's pick since clips open unmuted (it used to start muted and warn on unmuting). `letsClip.setVolume` sets the video's `muted` and `volume` itself: a `muted` attribute only mutes an element the HTML parser made, never one Blazor adds, so before v1.3 the preview played sound behind a muted icon.
- Leaving the editor cancels a running export. Exiting leaves a running export to the kill-on-close job, like a crash.
- The tray balloon can open another clip into the open editor: each loaded clip has its own lifetime (`_lifetime` token, its own `DotNetObjectReference` let go on detach, its pending trim written when it ends), so a probe or timeline strip still running for the last clip never lands on the next, and `ExportPanel` is keyed by the clip's path, so an export or a pick never carries over.
- A saved clip holds up to a second of keyframe pre-roll below zero behind its MP4 edit list: `ffprobe -show_packets` lists it with negative times and the discard flag, players never show it.
- A capture's FFmpeg is disposed only after its exit code is read (`SegmentProcess.Exited` always completes), so `ReplayRecorder.WatchEndAsync` never waits forever; `GameWatcher` reads and lets go of the found game's handle under one lock.
- A still game window's clip can end its video before its audio: the last frame holds while the sound runs on to the press.
- A warm-up clip's file starts with about a second of audio before the first video frame, and that first frame can show content older than its timestamp (`ddagrab` probes it at start); thumbnails come from a second in.
- The video FFmpeg holds about 600 MB of private memory, flat over a 10 minute run; the audio one about 23 MB.
- Opening the monitor list shows a `MonitorOverlay` on every monitor (accent edge and name on the picked one, grey on the others), and a pick stays outlined 1.5 s. They are placed and drawn at zero opacity, then all made visible in one dispatcher pass, since shown one by one the second monitor lit up a moment after the first. The overlays are click through, never activate and carry `WDA_EXCLUDEFROMCAPTURE`, so a screen grab or a clip never shows them even while buffering.
- The playhead draws above the trim handles at full height, so it never thins to half its width at the start or end; it is 3 px wide like each handle's grip line, which is centred by layout so it snaps to whole pixels.
- The trim handles sit outside the kept part, their inner edge on the time, so two handles never cross or overlap; the timeline pads both ends by a handle's width (`--handle-width`) and maps time over the inner `timeline-track`. The strip runs the timeline's whole width, under the handles too, and the outer shades stretch the same handle width, so no grey end shows without a picture; each handle's inner edge has a 1 px shadow in its own colour, which covers the seam a fractional position left beside the end handle. Dragging and arrow keys run in `AppShell.js`: it reads the range from the handles' `data-time`, paints handles, shades and selection itself, seeks the video, and tells Blazor once (`OnRange`) when a drag ends or a key steps, so no frame waits on a render. Blazor's next render matches what the script painted.
- Play runs from the playhead and stops at the end point, starting over from the start point once there; the 5 second jumps clear that stop when they pass it.
- The timeline strip decodes keyframes only, one a second, so it samples 12 frames over the duration less one second; spread over the whole clip, the last tile of a short one stayed black.
- A clip with no metadata reads its recording time from its generated name (`ClipNames.DateOf`), so a copied file keeps its date.
- WebView2's browser keys, zoom and pinch zoom are off (`AreBrowserAcceleratorKeysEnabled`, `IsZoomControlEnabled`, `IsPinchZoomEnabled`).
