# LetsClip

An instant replay recorder for one monitor or one game or app window that runs in the background, a lightweight Medal.tv in the owner's words. A WPF window hosts a `BlazorWebView` whose UI is MudBlazor, laid out like `SoTF.Editor`, with `WiFiWatch`'s tray and startup registration. It starts with Windows in the tray and keeps the last 30 seconds to 10 minutes of the chosen monitor (the primary until one is picked) or of a known game's or added app's window (`AFK-Assist`'s `GameScanner`), with system audio (or, with its Game and Voice Chat choice, just the game's and the voice apps' sound, voice chat at a level of its own) and a cleaned microphone, which also gets a track of its own beside the mix, in a rolling replay held in memory (past a gigabyte, or a sixteenth of the PC's memory, its oldest part waits on disk). Each game or app can record at its own resolution, frame rate and quality, set from its row in Games and Apps. A hotkey saves them as an MP4 clip of exactly that length, named after its game (`Overwatch 2026-11-14 21-05-33.mp4`), and Record keeps everything from its press until Stop as one clip. A replay outlives a crash, a closed game or a restart, so the moments before it still save. An unknown app filling a monitor for two minutes while nothing records is offered once, and the status chip and the empty Clips page say what records and open the fix when something is wrong, the chip's tooltip saying how much a save holds and Save, once a session ended, what it kept (`Save Last 5s`); a setting greyed for another setting's sake reads Not Used. During Record the tray tile turns red and its tooltip counts the time. With Notifications on (off by default) a save and a newly recorded game say so in a toast over a full screen game or a tray balloon; a clip that came out black always says so. The Clips page lists them under Today, Yesterday, This Week, Last Week and then each month, each header with its count and each clip tagged with its game, app or monitor, searches them, a menu on each card to rename, copy, copy for a Discord plan, copy its last export, show or delete it (with Undo) with its details nested, marks the ones saved since LetsClip was last open with a New chip, drags a card into Discord or a folder as a copy of its file, filters them by game, each with its count, or to the unedited ones as each box is ticked, and lists what was deleted from its header (Recently Deleted, read from the Recycle Bin), putting a clip back with its details, or a cut's whole clip back for Restore Original, in one click; the editor names a clip (renaming its file), trims it to the frame over a strip with the sound's waveform (the game's white, the microphone's darker grey on clips with separate tracks) that the mouse wheel zooms (a hint says so), cuts it losslessly (Export and Save, with Restore Original, which brings the full clip back from `.Originals` or, where the cut sent it to the Recycle Bin, straight out of the bin) and exports an exact copy of the selection, with or without the game's sound or the microphone or with the two balanced at their own levels, crops it to any part of the picture with a box that always lies over it, sized freely from its corners or one side at a time and reset in one click, leaves out the video for the sound alone (Ogg Opus, which Discord plays inline, under a plan; an exact `.m4a` copy under Off), or fits it under a Discord plan's limit as HEVC, down to 240p at 15 FPS so about 27 minutes fit Free with video and 89 without, exports pressed meanwhile waiting their turn, each row saying how long it will take and every number on the right following each drag live; every export that re-encodes sound evens its loudness toward -14 LUFS. Any clip copies to the clipboard as a file from its card's menu or the editor, whose main button copies instead of exporting whenever the export would only be the clip itself. Changing the clips folder moves everything with a progress bar. It installs itself as `LetsClip.exe` with an entry in Settings, Apps, checks for updates by itself, installs them in the background once it has sat hidden for a while and then says what changed, and Report a Problem opens a GitHub issue with its log on the clipboard. It runs on its own slim FFmpeg build, which sizes a game or app window with Lanczos on the graphics card and converts frames there for AMD and NVIDIA.

## Every Round, Start To Release

Do every step below, in order, every round, without being reminded: the owner should never have to repeat any of it. Be thorough and be sure. Measure rather than eyeball, look at every screen the round touched, and never call something done that was not seen working.

1. `git pull` first, since the owner edits the README on GitHub.
2. Read every file the change touches and its callers before editing. A problem the owner points out once is a pattern: search the whole app for the same control, wording, spacing or shadow and fix every place in the same round.
3. Build with `dotnet build LetsClip.slnx`: zero errors and zero warnings. A running sandbox locks `bin`, so stop it first.
4. Run every check: `dotnet format analyzers` and `dotnet format style` with `--verify-no-changes --severity info` on each of the three projects, `csharpier format .` then `csharpier check .`, `powershell -File ~/.claude/scripts/RazorStyle.ps1`, `git ls-files --eol` showing no `w/lf` and no `w/-text`, the comment length check over the C# and every CSS and JS file under `wwwroot`, and the Title Case scan of every label (`Docs/Verify.md`). Normalising line endings with `sed` gives a file without a final newline a lone CR at its end, which git then reads as binary (`w/-text`): trim that byte.
5. Run a ponytail ultra audit over what the round touched and anything it grew: dead parameters and fields, single use wrappers, markup repeated where one shared component belongs (like `ChoiceSelect`), settings nobody needs. Apply what it finds and say what was cut.
6. Look at it in a sandbox and run the standard test pass, both in `Docs/Verify.md`: the sandbox on the owner's second monitor, the sweep at three page sizes with every state measured and screenshotted, every touched control used for real, and a measured test on FFmpeg's own sources for any media change.
7. Update the docs for everything that changed: the topic files in `Docs` for what it does now and its rules, `Docs/Behaviour.md` for anything that looks wrong but is not, `Docs/History.md` for the day at its top (the owner's picks and what they replaced, the numbers measured, what was left for later), and this file for its layout, data and agreement.
8. Release only once the owner said publish; saying so for the round, or asking for the whole publish flow, counts:
   1. `git pull` again.
   2. Publish to a scratch folder with `-p:BaseOutputPath=<folder>\`, then take the screenshots as under Screenshots from that exe copied alone into an empty folder, which is also the release's lone exe test.
   3. Update the README to match what shipped, one short plain bullet per feature.
   4. Bump `<Version>` to the next patch (`1.8.5` after `1.8.4`) unless the owner names another.
   5. Commit everything as one short Title Case line with no body and no attribution, publish again from that commit (the exe embeds it as `AppInfo.Commit`, which the next update's What Changed compares from), and push to `master`.

Leave the owner's copy to update itself: once the release is live and verified, pushing it is enough, the owner's words of 18 November 2026, so nobody waits for the background update or restarts his copy to hurry it. ## Build, Run And Publish

The FFmpeg binaries are not in git. After cloning, once:

```bash
powershell -ExecutionPolicy Bypass -File LetsClip.Desktop/FFmpeg/Get-FFmpeg.ps1
```

```bash
dotnet build LetsClip.slnx
```

```bash
dotnet run --project LetsClip.Desktop
```

```bash
dotnet publish LetsClip.Desktop -c Release
```
