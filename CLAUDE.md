# LetsClip

An instant replay recorder for one monitor or one game or app window that runs in the background, a lightweight Medal.tv in the owner's words. A WPF window hosts a `BlazorWebView` whose UI is MudBlazor, laid out like `SoTF.Editor`, with `WiFiWatch`'s tray and startup registration. It starts with Windows in the tray and keeps the last 30, 60 or 120 seconds of the chosen monitor (the primary until one is picked) or of a known game's or added app's window (`AFK-Assist`'s `GameScanner`), with system audio and an optional microphone, in a rolling cache. A hotkey saves them as an MP4 clip of exactly that length. The Clips page lists them under their game's name with their resolution and frame rate and filters them by game; the editor names a clip, trims it to the frame, cuts it losslessly (Export and Save, with Restore Original) and exports an exact copy of the selection, or fits it under a Discord plan's limit.

## Build, Run And Publish

The FFmpeg binaries are not in git. After cloning, once:

```bash
powershell -ExecutionPolicy Bypass -File LetsClip.Desktop/FFmpeg/Get-FFmpeg.ps1
```

```bash
dotnet build LetsClip.slnx
```

```bash
dotnet run --project LetsClip.Desktop
```

```bash
dotnet publish LetsClip.Desktop -c Release
```

The publish folder holds only `LetsClip_v<Version>.exe`: `IncludeAllContentForSelfExtract` and the `BundleWebRoot` target pack `wwwroot` and the `FFmpeg` folder inside it, extracted once on first start. The exe is ReadyToRun (`PublishReadyToRun`), so the first page opens sooner. `LetsClip.Desktop` keeps the Windows SDK version in `net10.0-windows10.0.17763.0`: the app itself uses no WinRT, but `BlazorWebView`'s `WebView2CompositionControl` loads `Microsoft.Windows.SDK.NET` when the window loads. Plain `net10.0-windows` built and published 16.5 MB smaller and then failed there with a `FileNotFoundException`, the page never showing (tried in the November 2026 audit). A build without the FFmpeg files stops with a message (`RequireFFmpeg`, before `BeforeBuild`: hooked to `Build` it ran after the copy step, which failed first on the missing `LICENSE.txt`).

`.github/workflows/build.yml` fetches the pinned FFmpeg and builds in Release on `windows-latest` for every push and pull request. Releases are made by hand, the shared way: the exe as the only asset and an empty body, and only once the owner has tried the build left running for them and said publish. A patch number is the owner's pick when asked for (1.8.2, released on 6 November 2026); `AppInfo.VersionText` then shows three parts. Every shown version reads like its tag, `v1.8.2` (`AppInfo.VersionText` carries the `v`): the update snackbar, About and the update dialog. From PowerShell, `gh release create` takes the empty body as `--notes-file` of an empty file: PowerShell drops an empty `--notes ""` argument, which shifted the exe into the tag position. After a release check that `releases/latest` redirects to the new tag and that the asset's `digest` matches the local exe, since `Updater` refuses an update without it.

The owner's install lives in `%LocalAppData%\Programs\LetsClip` (v1.8 placed there on 6 November 2026). A build left running for the owner goes there through an `explorer.exe`-started `.cmd`, so it runs outside the app container on the real profile and its first Release start rewrites the Run value and the Start Menu shortcut to that path; a test exe started anywhere else leaves the Run value pointing at it, which happened with a v1.7.1 test build that was later deleted. Killing the owner's copy mid recording can hang AMF for the next start, as it did on 8 November 2026 (the install script started the new exe 3 s later, its 1080p60 session timed out at 12 s and fell to x264), so the script waits 10 s before starting it.

A Release exe someone started from `bin\Release` locks that folder; publish to another folder with `-p:BaseOutputPath=<folder>\` rather than stopping it. A `BaseOutputPath` outside the project lets the project's own `bin` folder into the publish folder as content (`bin\Debug\...\*.json` showed up beside the exe), so the release asset itself is published to the default `bin\Release` once nothing runs from there.

## Automatic Recording

- Recording has no switch, the owner's pick (a Buffer in Background switch, a first run notice and a tray pause all came and went): `CaptureController` starts it at launch, after an unlock, a wake, the display coming back and a monitor returning, and only Exit ends it. Every word on screen says Recording, never Buffering: the chip and tray read Recording, Recording Overwatch, Waiting for a Game or App, Saving Clip or Not Recording.
- People set it once and forget it, so every failure retries by itself (`ReplayRecorder.Failed`, `CaptureController.RetryAsync`): 2 s, then 5, 15 and 30 s, then each minute, a failed start and a dropped session alike; the count starts over only when a session had run 30 s, so a capture that starts and dies at once keeps backing off. Any exception a start throws ends on Error and retries, a COM error from a restarting audio service too, never stuck on Starting. Retries stay out of sight, the owner's rule (see Recovery): `CaptureController.ShowsError` stays false for the first four failures in a row (`QuietFailures`, about a minute), so the chip, tray and Save button read Recording and a press waits for the restart. Only a failure that lasts past that, or one the person must fix (`CaptureBlockedException`: HDR on, under 2 GB free, FFmpeg missing, the monitor gone), shows the error with Try Again, while the retries go on (HDR turned off or space freed starts recording within the minute). Killing the video FFmpeg of a running session restarted it 5 s later with the chip on Recording throughout. A closed game ends its window capture before `GameWatcher` notices (up to 2 s), so a window session whose window is gone (`MonitorCatalog.ClientSizeOf` null) ends quietly too, logged as Stopped Recording, The Window Closed: a game closed 5 s into its session went from Recording to Waiting for a Game or App in 0.8 s, where it used to flash Recording Error; a game that recreates its window restarts the same way.
- `CaptureHolds` (locked, asleep, display off, exiting) stop it and clear the history; it starts again only when no hold is left. Displays that sleep after the Windows timeout count, so an app left alone stops recording on its own.
- A saved monitor that is unplugged falls back to the primary, so recording never sits idle without a word; it moves back when the monitor returns. `CaptureController.DisplaysChangedAsync` names what happened to the running monitor (disconnected, or its display settings changed) and restarts only what differs. 30 FPS is always offered, even on a 24 Hz screen.
- A start that throws anything (a blocked FFmpeg, an unwritable cache) ends on Error, never stuck on Starting. An encoder test that fails or hangs past 20 s counts as failed and the next encoder takes over, with the warning naming it; it is tried again at the next start, and only passes are cached (`VideoEncoders.WorksAsync`). AMF sometimes hangs at init right after another AMF process was killed: seen twice in the November 2026 sweep, where a hung test once left the 1440p144 start on Error. A hardware encoder's capture gets two starts before the next encoder takes over, so one hang does not leave a session on the CPU. Falling back shows nothing any more, the owner's pick after `Using x264 on the CPU, AMD AMF failed` worried them: the clip is fine, only the CPU works harder, and `ReplayRecorder.UpgradeAsync` moves back by itself (see Recovery). A timed out start logs which half went quiet (`Capture Start Waited`, frames and first segments), since the one real case left no other clue.
- `ReplayRecorder` raises `StatusChanged` only when the status really changes, and its health check ticks only while a session runs: the tray and an open page no longer wake every second.
- Games Only records the game's own window, never the desktop: alt tab, chats and notifications stay out of the clip. `GameWatcher` scans the running processes every two seconds for a known game with a window on screen (not minimised), so a game started before LetsClip is found too, and counts it until its process exits, read from that one process's handle without listing processes again. It scans only while Games Only is on and nothing holds capture. Games Only can be turned on with no known game, the owner's pick: it then waits for one, Waiting for a Game or App on the chip. Since any app can be added, every word on screen says Games and Apps (the switch reads Games and Apps Only, the capture panel row Game or App, the dialog Games and Apps with Add Game or App); the setting keeps its `GamesOnly` name. Taking the recorded game off the list stops its recording at once (`GameWatcher.SetGames` lets go of it); before, it kept recording until the game exited. Known games are `GameScanner`'s Steam, Epic, Riot, Rockstar and Roblox libraries plus `Games` folders on C, D and E, with `UserSettings.AddedGames` added and `RemovedGames` taken out (`CaptureController.GameList`). Turning Games Only on or off stops the capture and starts the other source.
- Settings → Games and Apps Only → the Edit Games and Apps button (never a count, the owner's pick) opens `GamesDialog`: a search field (`MudHighlighter` marks matches) over one outlined table with no header and no cell borders, each row the exe's own icon, the name and a switch. ## Capture

- Monitors: `ddagrab` (Desktop Duplication) on the adapter and output that `MonitorCatalog` finds for the saved monitor's device path, never a stored index. The frame comes back unrotated: rotation 90 is `transpose=clock`, 270 `transpose=cclock`, 180 both flips (checked on the portrait LS27AG500N at 270).
- Game windows: `gfxcapture` (Windows Graphics Capture) on the window handle `GameWatcher.GameWindow` reads fresh at each start, with no yellow border, sized to the window's own shape inside the resolution box of the monitor holding it (`MonitorCatalog.ClientSizeOf`, `ReplayRecorder.FitInside`, never upscaled), so a maximised or windowed app gets no bars; only a window resized mid session is letterboxed (`resize_mode=scale_aspect`). The bars a v1.2 clip showed were that padding, never the desktop around the window. It sends a frame only when the window changes, so keyframes are forced each second of time (`-force_key_frames`), and the video stall check and slow frame rate warning are off for it: a minimised game sends nothing and only its exit ends the session, while a hung encoder is caught by a probe (see Recovery). A window still from its first moment sends one frame, which AMF and x264 both hold (`-latency 1 -async_depth 1` did not release it on AMF, only x264's `zerolatency` did), so no segment ever closes; up to v1.7 such a start failed every encoder after 12 s and retried with an error, which a paused YouTube window hit on 6 November 2026. A window session now counts as started once its audio writes a segment, or at the 12 s timeout while FFmpeg still runs (`CaptureSession.LaunchAsync`), since `VideoEncoders.WorksAsync` already proved the encoder; video flows the moment the window draws, and a save before that says `Nothing has moved in the window yet`. An `overlay` onto a paced `color` source does not help: frame sync waits for the window's next frame too.
- Resolution is a select of `UserSettings.ResolutionChoices` (480p, 720p, 1080p, 1440p, 2160p) below the picked monitor's short side plus the monitor's own size, labelled by that side (`CaptureController.ResolutionChoices`). A choice fits its 16 by 9 box in the monitor's orientation, never up (`ReplayRecorder.OutputSize`, 480p is 854 x 480); one at or above the short side is the monitor's own size. The saved value is the picked lines (`UserSettings.Resolution`, 1080 by default), and a monitor without it takes the nearest below, like frame rates. Frame rates are `UserSettings.FrameRateChoices` up to the monitor's refresh rate, which `MonitorCatalog.DisplayDetails` takes from the `QueryDisplayConfig` path's own fraction rounded with `Math.Round` (59.94 Hz reads 60, 143.86 Hz 144, never 59 or a decimal), the owner's pick; every shown rate, log and choice uses that one number. `DEVMODE`'s `dmDisplayFrequency` truncates, so it read 59 on a 59.94 Hz screen.
- `hwdownload`, then one CPU `scale` with Lanczos and BT.709 limited range, then `nv12`. Lanczos costs nothing over bilinear and scores 10 VMAF higher (see the Overwatch Field Test). On the CPU route a window up to 2560 x 1440 is read back at its own size and this `scale` sizes it (`CaptureSession.MaximumWholeWindowPixels`); above that, and on Quick Sync, `gfxcapture` still sizes it on the GPU, since a 4K readback costs a core. Measured with the window shown: 2560 x 1440 to 1080p at 60 FPS takes about half of one CPU core for the video process, 2560 x 1440 native at 240 FPS about two cores and 606 MB, holding 240 FPS (7198 frames in a 30 s clip).
- Intel Quick Sync converts on the GPU instead (`VideoEncoders.QuickSyncGpu`, `GpuFrames`): `hwmap=derive_device=qsv`, then `vpp_qsv` sizes, turns (`transpose` clock, cclock, reversal) and makes `nv12` with BT.709 limited range. Measured in November 2026 on an i5-1335U with Iris Xe and FFmpeg 9.0.2: Desktop Duplication at 1080p60 takes 21% of a core against 83% on the CPU route, window capture 4.8 against 13.9 ms of CPU per frame, both holding the rate (10,798 frames in 3 minutes with a build running); colour bars score 43.9 dB for the conversion alone (CPU `scale` 42.6) and 48.6 after encoding (45.1), limited range on both. Downscaling 1440p to 1080p is softer (40 to 42 dB against Lanczos in every `scale_mode`, CPU bilinear 44.3), so only a monitor above 1080p recorded at 1080p differs. A failed GPU start falls back to the CPU route on the same encoder without a warning. `scale_d3d11` fails on Iris Xe too (`E_INVALIDARG`); AMD and NVIDIA keep the CPU route, NVENC untested.
- AMD and NVIDIA keep the CPU route, the owner's pick after a full GPU research on 6 November 2026 (RX 9070 XT, FFmpeg 9.0.2, a YouTube video playing): it is simple, the same for every GPU vendor and both capture modes, and already as light as the popular tools. A published 1080p60 test on a Ryzen 7 7700X put ShadowPlay at 2.4% of the whole CPU, Xbox Game Bar 3.7% and Medal 5.1%; LetsClip's 1080p60 monitor capture is 40 to 55% of one core, 5 to 7% of the owner's 7800X3D (which reports 8 threads), and window capture, the default, about 19% of one core. Those tools keep frames on the GPU and convert colour there (OBS hands NV12 textures to its GPU encoders); LetsClip downloads each frame and converts it with `scale`, which costs most at high frame rates, never at 1080p60. What the research found, all with `-frames:v 120` runs so no AMF process was killed:
  - AMF encodes D3D11 NV12 textures (a `hwupload` of NV12 into `h264_amf` worked) but refuses D3D11 BGRA (init fails with -22 for uploaded BGRA, `SubmitInput` fails for `ddagrab` frames), so a GPU route needs a BGRA to NV12 step on the GPU.
  - `scale_d3d11` (options `width`, `height`, `format`, only `nv12` or `p010`) cannot create its output pool on AMD: `Could not create the texture (80070057)` even for uploaded test frames. Its pool asks for `D3D11_BIND_RENDER_TARGET | D3D11_BIND_VIDEO_ENCODER` in a texture array of 10, and AMD's D3D11 driver has no D3D11 video encoder, so the bind flag is the likely cause. It fails the same way on Iris Xe. When a newer FFmpeg drops that flag, `hwdownload`, `format=bgra` and `scale` become `scale_d3d11=width=W:height=H:format=nv12` straight into the encoder for every vendor and both modes: recheck on every FFmpeg update.
  - `vpp_amf` refuses D3D11 input (`AMFConverter-Init() failed with error 10`, not supported) from `ddagrab` and from an upload alike, but converts AMF surfaces fine (`vsrc_amf`, or BGRA uploaded to an `amf` device).
  - `hwmap=derive_device` from `d3d11va` to `vulkan` or `d3d12va` is not implemented (-40), to `amf` fails (-22), so `scale_vulkan`, libplacebo, `h264_vulkan` and `h264_d3d12va` cannot take capture frames. `h264_mf` on `ddagrab` frames fails with a generic external error.
  - The one working GPU-only route is AMD's own capture: `-init_hw_device amf=a -filter_hw_device a`, `vsrc_amf=monitor_index=0:framerate=R`, `vpp_amf=w=W:h=H:format=nv12:color_profile=bt709:out_color_range=studio`, `h264_amf` (it cannot take `vsrc_amf`'s BGRA itself: `encoder->Init() failed with error 10`). Over 30 s its FFmpeg used 8% of a core at 1080p30 against 30%, 20% against 41% at 1080p60, 21% against 69% at 1440p60, 19% against 29% at 720p60, 36% against 98% at 1080p120 and 46% against 132% at 1080p144, the video engine as busy as before. It is not used: it captures monitors only, never a window, so the default mode gains nothing; it is AMD only, so a second pipeline next to the one every vendor needs; its framerate tops out at 200 (`Failed to set framerate: 5` from 210 up), so 240 still needs the CPU route; it opens every session with 0.63 to 0.79 s of nothing, its stamps jitter (60 repeated at 1440p60) and it ran 9 to 11 frames short in 30 s at 120 and 144 FPS (one 10 s run gave 40 FPS at 60); and its own capture thread polls, `capture_mode=wait_for_present` sends only on presents (16 FPS), `get_current` spins a core at 278 FPS. It turns a portrait monitor upright by itself (1440 x 2560) and has no cursor option; whether it draws the cursor was never seen.
  - Downloaded BGRA fed to AMF halves the CPU at 240 FPS (0.84 cores against 1.70), but AMF's own conversion scored 36.6 dB on colour bars against 44.6 dB for the `scale` above, and its range follows the input's tags (full range from `ddagrab`), so it is not used. `fast_bilinear` saves no CPU per frame and drops to 39.6 dB. Converting to `nv12` before scaling, or `scale` with `threads=4`, saved nothing at 144 or 240 FPS: what limits 240 FPS on a 2560 x 1440 monitor is reading the frames back from the GPU, about 3.5 GB/s. Colour checks use known bars, never the live screen, whose frames already differ at 24 dB.
- The first Quick Sync use from a freshly written FFmpeg copy is slow on the i5: the first encoder test after the v1.7 build and the v2.0.1 update took 7.6 and 9.3 s, a harness's new FFmpeg copy 6.3 s, and every later one 0.55 to 0.75 s, the GPU idle for 5 minutes or not. It is not the exe's path alone (a copied folder took 1.1 s), not the GPU's idle state and not the D3D shader cache (nothing written during it); the cause was not found and no public report matches. So in Games Only, where the start waits for a game, `CaptureController.StartAutomaticallyAsync` runs the first encoder's test in the background at launch for the picked monitor's box and frame rate (`WarmUpEncoderAsync`): the slow first test after an update lands where nobody waits, and its pass is cached, so a fullscreen game on that monitor skips the test entirely. A start during it runs its own test beside it; sharing one was left out, since an export's test carries its cancel.
- The encoder is the first that really encodes a few test frames (`VideoEncoders.WorksAsync`): AMF, NVENC or Quick Sync for each GPU vendor present, then x264. A one second GOP, no B frames, and `h264_metadata` writes the BT.709 colour description the hardware encoders leave out. Rates grow with the pixel rate: load is the square root of pixels per second over 1080p60, at least the frame's own share of 1080p (1 from 1080p up, 0.67 at 720p, 0.44 at 480p), the average 20 Mbps and the peak 40 Mbps times the load. Only AMF and x264 are tested on this PC. x264 captures with four threads (`-threads 4`): by default it starts about one and a half per core, each holding frames, so a 1080p60 monitor capture held 643 MB and dropped to 56 FPS on the i5's 12 threads; four threads hold 318 MB and 60.4 FPS through the app's own session, two 270 MB, and a noisy 1080p60 pattern scores the same either way (38.33 dB, 13.2 MB). Thread caps change nothing on the GPU routes (Quick Sync 217 to 247 MB whatever `-filter_threads` or `-async_depth`), so only x264 gets one.
- Quality is Normal, High or Max (`CaptureQuality`, Normal by default): High gives 1.75 and Max 2.5 times the average and peak bits, with quality level 22, 19 or 16 for NVENC's CQ, Quick Sync and x264's CRF, and 42, 48 or 51 for AMF's QVBR, which counts up (`VideoEncoders.TuningOf`); the replay cache grows with the peak. Up to v1.2.1 AMF got 22, 19 and 16 too, so Max recorded worse than Normal on AMD: a 1440p clip of a film came out at 1.18 Mbps. The AMF levels are matched to x264 by PSNR on a noisy 1440p60 pattern (AMF 42 32.13 dB at 33 Mbps against CRF 22 32.11 dB at 28 Mbps, AMF 48 32.23 dB against CRF 19 32.25 dB). Rechecked on 6 November 2026: on real footage (a 1440p YouTube clip scaled to 1080p) levels 44, 46, 48, 50 and 51 gave 36.5, 39.7, 41.7, 43.2 and 46.9 Mbps, so High spends about 27% and Max 43% more than Normal; on pure random noise High and Max came out byte for byte the same (59.1 Mbps), and with heavy noise AMF's QVBR ignored `-maxrate` (327 Mbps against 40M), which only `SegmentCache`'s byte bound then limits. - One second MPEG-TS segments from the `segment` muxer, each listed on standard output as `name,start,end`, with `mpegts_copyts=1` so the files keep the media clock. `SegmentCache` keeps the replay length plus three seconds, within 1.5 GB or the replay length at the peak rate plus 20%, whichever is larger, and never evicts past a pinned save.
- Noise Cancellation (`UserSettings.NoiseCancellation`, on by default, always shown under Microphone and disabled while the microphone is off) cleans only the microphone: `AudioMixer` then writes four channels, system audio on the first two and the microphone on the last two, and the audio FFmpeg runs `CaptureSession.MicrophoneCleaning` (`highpass` at 80 Hz, `afftdn` at 20 dB with noise tracking from a -45 dB floor, then `agate` at -40 dB, ratio 3, 24 dB down, 5 ms attack and 250 ms release) on those before `amix` puts them back to stereo. The owner still heard the room with v1.8.4's chain (12 dB, a -50 dB gate): measured on a synthetic voice at -30 dB RMS over pink noise, it took a -47 dB room only to -53 dB, since that gate opened on the room itself. The current chain takes the same room to -78 dB and a -41 dB room to -51 dB, while a -30 dB voice and a quiet -38 dB one keep their level within 0.6 dB and a word's first 50 ms reads as before. There is no strength setting, the owner's pick: one gentle sensitivity for everyone. Measure any change the same way (`aevalsrc` harmonics gated on and off, `anoisesrc` pink at 0.03 and 0.06, `astats` RMS of a gap, a word and its onset) before shipping it.
- Audio runs in a second FFmpeg process. In one process the scheduler held the live video back whenever the piped audio lagged the video by 100 ms, and capture fell to 6 FPS; apart, both run free.
- `FFmpeg.Start` opts every child out of power throttling (`SetProcessInformation`, execution speed and timer resolution). A sibling FFmpeg started outside LetsClip never slowed, which is how it was found.
- Monitor frames are timed by their count, not by `ddagrab`'s stamp: `ddagrab` stamps each frame with the moment it was grabbed, rounded to the frame grid, so with the CPU busy (a game plus the encoder) a late grab took the next slot and the one after it doubled up, a frame held twice as long. A 30 s Overwatch clip at 1080p60 had 15 of them, a 30 s x264 test 115, and a 240 FPS clip read as jumping and pausing. `setpts` now puts frame N in slot N from the first frame and re-anchors only past 1.5 slots of real drift (`CaptureSession.VideoArguments`); the same load then gave 1803 frames all 16.7 ms apart. Capture alone, idle, was always exact. Window capture keeps its own stamps, since a window sends frames only when it changes, and `-fps_mode vfr` drops a second frame that rounds into a slot already taken: with `passthrough` a 60 FPS window clip of a 240 Hz window held 1873 frames, 73 of them stacked on a used slot, and a 144 FPS one 1108; with `vfr` the 60 FPS clip holds 1800, all 16.7 ms apart. Rounding alone still dropped 10 to 25% of the frames whenever a game drew at about the capture rate (a 60 FPS game at 60, 120 at 120), since presentation jitter put two neighbours in one slot and left the next empty: a test window drawing at about 115 Hz kept 3221 of 3600 frames at 120 FPS. A window frame whose slot is taken now takes the next one, at most one slot late, and only a frame two slots behind its predecessor drops (`ld(3)` holds the last slot, `CaptureSession.VideoArguments`, November 2026): the same window keeps 3432, every frame it delivered, and a simulation of 120 on 120 and 144 on 144 went from 909 and 630 drops in 30 s to none, a 59.9 or 60.1 FPS game at 60 from about 490 drops in two minutes to 0 and 11. A window frame then sits at most 1.5 slots after its real time. Slower windows keep their empty slots (a 144 FPS clip of a 100 Hz window holds some frames for two slots), as any sampling of them would.
- The media clock: `AudioMixer` places each WASAPI packet at its QPC time (sample zero is the session's start, media time 1.0), silence and gaps stay silence, and a packet within 20 ms of the last one continues it. Device clocks drift from QPC (the owner's G522 headset loopback runs 16.7 ppm slow, steady over 12 minutes), so a continued packet more than 2 ms from its QPC time slews one frame toward it, repeating the previous sample or overwriting one (`DriftFrames`); before, it ran on until 20 ms apart and then jumped, a 20 ms gap every 20 minutes on that headset and every few minutes on a worse one. A 200 s session logged `Slewed System Audio By 67 Frames` (about 64 expected) and its clip had no gap. Video gets onto the same clock with one wall clock reading at its first frame (`setpts` with `RTCTIME`). Both clocks are read in microseconds.
- The audio process shifts its output with `-output_ts_offset`: FFmpeg 9.0.2 ignores `-itsoffset` on the raw `f32le` pipe, which left v1.2's audio on a clock one lead second early, so every clip played its sound about 0.94 s before the picture (measured with a flashing window and a 20 ms WASAPI beep). Since the fix the beep lands 11 to 54 ms after the flash over ten beeps.
- A save pins the cache, waits for the segment holding the key press to close, joins the segments with the `concat:` protocol and stream copies them up to the press into an MP4 named `LetsClip yyyy-MM-dd HH-mm-ss.mp4` (`ClipNames`). WebView2 and FFmpeg both honour it: a clip whose hidden pre-roll is red shows no red frame in the editor, and an export from it matches the source at 44.5 dB against 19 dB half a second off. A session younger than the replay starts at its first sample instead (media time 1.0). It runs off the UI thread and returns before any thumbnail is made (the library makes it later). A monitor save took 1.5 to 2.2 s from press to file on the i5.
- A still game window sends no frames, so its segment never closed and a save waited out its 8 s limit (9 s for a Claude window). Window sessions write their video segments with `flush_packets=1`; after 1.5 s the save joins the open segment (the newest `seg_` file) as it stands on disk, its last frame holding to the press while the audio runs on, shifted to the replay's start with `-itsoffset` when it is older than that. At most the encoder's last few held frames are missing. Measured on the i5: 2.2 s from press to file, for a window still 10 s (moving video, then its last frame) and still 40 s (one frame, 30 s of sound).
- Quick Sync ignored the forced keyframes as split points until `-forced_idr 1` (AMF and NVENC already force IDR): a game window's segments then closed only every 60 encoded frames, or never while still, which is what made that 9 s save.
- A clips folder on a drive that is gone saves to `Videos\LetsClip` instead, so the replay is kept, and the balloon then shows that file in Explorer (folders compare through `FilePaths.AreSame`, case and a trailing slash aside); save errors read as plain words (`ReplayRecorder.SaveErrorOf`). `ClipMetadata.FrameRate` keeps the capture rate, which exports prefer over a window clip's low probed average.
- While a save runs (`CaptureStatus.IsSaving`, from the hotkey, the tray or the button) the Save button's icon is a spinner in the icon's place (`button-spinner` inside a `mud-button-icon-start` span) and a second press does nothing; the chip reads Saving Clip. A save plays `SaveChime` (two soft bell notes a fifth apart, a third of a second whose last 30 ms fade to silence, played by `PlaySoundW` from a pinned buffer so any thread can call it; `SoundPlayer` raced on two quick saves) instead of the Windows sound, when Save Sound is on, the moment the save is accepted (`ReplayRecorder.SaveStarted`), not when the file is written; the balloon still waits for `ClipSaved`; `SaveChime.Play` first has `AudioMixer.MuteSystemAudio` write the loopback as silence for that long, so the chime never lands in the next clip. Its volume is `UserSettings.SaveSoundVolume` (full by default, the owner's pick, 10% to 100% in tenths): `SaveChime` renders one pinned wave per tenth on first use, and Settings sets it with the same `VolumeButton` the editor uses, with no switch beside it, the owner's pick: a press turns it off or on, sliding to zero turns it off and keeps the last level, turning it on plays the chime at once and sliding plays it once, 300 ms after the last step, and off reads red like the export's Audio and a muted player. The owner pressed it several times and heard nothing until it suddenly worked, while the meter showed every call reaching the Windows output within 60 ms (`AudioMeterInformation`, no stream opened): with nothing else playing the output wakes slowly and swallows the first third of a second. Each `PlaySoundW` call cuts the one before, so the old play on every step left only clipped starts, which read as no sound at all (measured on the loopback: every call reaches the mixer about 80 ms later). - Lock, sleep, display off, a monitor change and a stalled encoder all end the session and clear its history; nothing splices across them.

## Looks Wrong, Is Not

- Each capture writes two segment streams (`seg_` video, `aud_` audio); the save joins them by their shared timestamps.
- `ClipSaver` writes the clip as `.LetsClip-<guid>.mp4` and renames it only after it probes back; such leftovers after a crash are ignored by the library and never deleted, since the clips folder belongs to the user.
- `CacheFolders.Delete` refuses anything but a GUID folder directly under the cache root and only deletes files named like segments or x264 pass logs.
- The preview plays with sound while recording, so its sound lands in the next clip, the owner's pick since clips open unmuted (it used to start muted and warn on unmuting). `letsClip.setVolume` sets the video's `muted` and `volume` itself: a `muted` attribute only mutes an element the HTML parser made, never one Blazor adds, so before v1.3 the preview played sound behind a muted icon.
- Leaving the editor cancels a running export. Exiting leaves a running export to the kill-on-close job, like a crash.
- The tray balloon can open another clip into the open editor: each loaded clip has its own lifetime (`_lifetime` token, its own `DotNetObjectReference` let go on detach, its pending trim written when it ends), so a probe or timeline strip still running for the last clip never lands on the next, and `ExportPanel` is keyed by the clip's path, so an export or a pick never carries over.
- A saved clip holds up to a second of keyframe pre-roll below zero behind its MP4 edit list: `ffprobe -show_packets` lists it with negative times and the discard flag, players never show it.
- `ExtendedLimits` (`FFmpeg`) and `AdapterDescription` (`MonitorCatalog`) are explicit layouts holding only the fields read, at their 64 bit offsets, like `ModeInfo`; the app is x64 only. Checked after the change: children die with a killed parent and the AMD adapter is still found.
- A capture's FFmpeg is disposed only after its exit code is read (`SegmentProcess.Exited` always completes), so `ReplayRecorder.WatchEndAsync` never waits forever; `GameWatcher` reads and lets go of the found game's handle under one lock.
- A still game window's clip can end its video before its audio: the last frame holds while the sound runs on to the press.
- A warm-up clip's file starts with about a second of audio before the first video frame, and that first frame can show content older than its timestamp (`ddagrab` probes it at start); thumbnails come from a second in.
- The video FFmpeg holds about 600 MB of private memory, flat over a 10 minute run; the audio one about 23 MB.

## Recovery

The owner's rule: consistent on every kind of system, and anything that can fix itself does so without the person noticing. Only what lasts or what they alone can fix is ever shown. Add every new failure to this table.

| What goes wrong | What happens | What the person sees |
|---|---|---|
| A hardware encoder's capture hangs or fails to start | The same encoder gets a second start (12 s limit each), then the next one | Recording throughout |

## Reliability Research And Tests

Done on 8 November 2026 after `Using x264 on the CPU, AMD AMF failed` appeared. Keep the conclusions; rerun the tools below whenever capture, encoders or recovery change.

- What happened: the installer step force killed the owner's copy mid recording and started the new exe 3 s later. Its encoder test passed in 1 s, then the real capture produced nothing for 12 s and fell to x264. The log held no FFmpeg error, which is why starts now log which half went quiet.
- It could not be reproduced: 140 cycles of starting `ddagrab` into `h264_amf` and killing it, restarting at once or after 3 s, and 20 with a graceful `q`, gave 0 hangs, first frame at 590 to 720 ms, the single failed run never repeating. So a graceful stop was not added, and nothing depends on knowing the cause: two starts plus `UpgradeAsync` cover it either way.
- AMD: no public report of AMF hanging after a killed process was found; an OBS issue shows AMF deadlocking at shutdown on one preset, fixed by a newer driver. AMF refusing `qvbr` on old cards would fail `WorksAsync` and fall to x264.
- NVIDIA: consumer cards cap concurrent NVENC sessions (2, then 3, then 5 in the support matrix), so OBS or another recorder can use them up. A start then fails, x264 takes over and `UpgradeAsync` moves back once a session frees up. NVENC is still untested on real hardware here.
- Intel: on hybrid machines `h264_qsv` can fail with `unsupported (-3)` when the Intel adapter drives no display, so it falls to the next candidate.
- Hybrid laptops: Desktop Duplication returns `DXGI_ERROR_UNSUPPORTED` when run on the GPU that does not drive the display; `MonitorCatalog` passes the adapter that owns the output, so this is already handled. FFmpeg ticket 10385 (ddagrab on non primary outputs) was fixed by 7.1.1 and we ship 9.0.2.
- Software rendering: `backdrop-filter` is slow without a GPU in some engines, Chromium 140 handles it. Capture needs a GPU anyway, so nothing was changed.
- Injected failures, through the stand-in `ffmpeg.exe` below, on a window session with AMF: a hang on the first capture, three failed rounds of all encoders, the audio process dying at 6 s, the encoder test hanging, the video process dying at 35 s and a hang 10 s in all stayed on Recording with no error shown. A window still from its first moment kept its session, with both probes hung or not. A save pressed during retries waits and saves what the new session holds (1.3 s of it, 12 s later).
- Cost with the window open on the 7800X3D, Debug: Clips idle 0.5% of a core and WebView2 0%, the hover preview 5.9% and 27% only while it plays, Settings idle 0% and 0.2%, the live microphone test 2% and 1.4% plus 0.5% for its FFmpeg.

- Scales: Clips, Settings and the editor measure clean (no sideways scroll, nothing past its panel, no side panel scroll) at the page sizes Windows gives 1080p at 100, 125 and 150%, 4K at 200%, 1440p at 100% and 768p at 100%.

The matrix harness steps `CaptureController.UpdateSettings` through each setting, waits until `Recorder.Options` matches, samples the FFmpeg processes' `TotalProcessorTime` and `\GPU Engine(*)\Utilization Percentage` for their pids over 10 s, saves through `CaptureController.SaveAsync`, and reads each clip's packet times with `ffprobe -show_entries packet=pts_time`; it then exports a clip at several limits and ranges, with and without sound, through `ClipExporter`. Window capture is tested on a small WinForms file-based app keyed as a game (`pattern`, moving or `still`), never on the owner's apps. `StartupRegistration` is checked in Release without and with `LETSCLIP_ROOT`, removing the Run value and shortcut afterwards.
- `TestClips/` holds three neutral clips from FFmpeg's `testsrc` and `sine`, never a real recording, about 3 MB in all (x264 `-crf 40 -preset veryslow`): `LetsClip 2026-11-06 08-30-35.mp4` (30 s, 1920 x 1080 at 60 FPS, 440 Hz), `LetsClip 2026-11-05 12-16-02.mp4` (30 s portrait, 1080 x 1920 at 60 FPS, 660 Hz, for the editor's sizing) and `LetsClip 2026-11-01 08-42-10.mp4` (2 minutes, 1280 x 720 at 30 FPS, 330 Hz, for `1m30,5s`).
