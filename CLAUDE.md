# LetsClip

An instant replay recorder for one monitor that runs in the background. A WPF window hosts a `BlazorWebView` whose UI is MudBlazor, laid out like `SoTF.Editor`, with `WiFiWatch`'s tray and startup registration. It starts with Windows in the tray and keeps the last 30, 60 or 120 seconds of the chosen monitor (the primary until one is picked) and system audio (optional microphone) in a rolling cache, all the time or only while a game runs (`AFK-Assist`'s `GameScanner`). A hotkey saves them as an MP4 clip of exactly that length, and the clip editor trims it and exports an MP4, under a size limit when one is needed.

| Project | Holds |
|---|---|
| `LetsClip.Data` (`net10.0`) | `Helpers` (`AppInfo`, `Formatter`, `ClipNames`, `SizeBudget`, `TrimRange`, `Hotkey`, `FilePaths`, each with a Debug self test), `ViewModels` (records the UI and services share), `Enums` (`CaptureHolds` among them) |
| `LetsClip.Services` (`net10.0-windows`) | `Capture` (`ReplayRecorder` state and saves, `CaptureSession` the two FFmpeg processes, `AudioMixer` WASAPI onto the media clock, `SegmentCache`, `ClipSaver`, `MonitorCatalog` DXGI, display config and refresh rates, `AudioDevices`, `CacheFolders`, `CaptureController` the app's one entry point, its automatic buffering and the games list), `Games` (`GameScanner` copied from `AFK-Assist`, `GameWatcher`), `Integration` (`StartupRegistration` copied from `WiFiWatch`, `Updater`), `Media` (`FFmpeg` process runner with a kill-on-close job, `MediaProbe`, `VideoEncoders`, `ClipLibrary`, `ClipExporter`), `Storage` (`UserSettings`) |
| `LetsClip.Desktop` | `App` (startup, `--tray`, logging, single instance, lock, sleep and display events), `MainWindow` (WebView2 host, tray, close to tray, virtual hosts), `Interop` (`DesktopShell` for the page, `MonitorOverlay`, `WindowMessages` for the hotkey and display power, `TrayMenu`, `TrayBalloon`, `SaveChime`, `Explorer`, `WindowCaptionTheme`), `Components`, `Theming`, `wwwroot`, `FFmpeg` |

Packages: MudBlazor, `Microsoft.AspNetCore.Components.WebView.Wpf`, NAudio.Wasapi 3, NLog. FFmpeg 9.0.2 (BtbN GPL shared build, pinned by SHA-256 in `LetsClip.Desktop/FFmpeg`) does capture, encoding, segmenting, remuxing, probing, thumbnails and export as child processes. No database.

## Build, Run And Publish

The FFmpeg binaries are not in git. After cloning, once:

```bash
powershell -ExecutionPolicy Bypass -File LetsClip.Desktop/FFmpeg/Get-FFmpeg.ps1
```

```bash
dotnet build LetsClip.slnx
```

```bash
dotnet run --project LetsClip.Desktop
```

```bash
dotnet publish LetsClip.Desktop -c Release
```

The publish folder holds only `LetsClip_v<Version>.exe`: `IncludeAllContentForSelfExtract` and the `BundleWebRoot` target pack `wwwroot` and the `FFmpeg` folder inside it, extracted once on first start. The exe is ReadyToRun (`PublishReadyToRun`), so the first page opens sooner. A build without the FFmpeg files stops with a message (`RequireFFmpeg`, before `BeforeBuild`: hooked to `Build` it ran after the copy step, which failed first on the missing `LICENSE.txt`).

`.github/workflows/build.yml` fetches the pinned FFmpeg and builds in Release on `windows-latest` for every push and pull request. Releases are made by hand, the shared way: the exe as the only asset and an empty body. A patch number is the owner's pick when asked for (1.1.1); `AppInfo.VersionText` then shows three parts.

A Release exe someone started from `bin\Release` locks that folder; publish to another folder with `-p:BaseOutputPath=<folder>\` rather than stopping it.

## Where Data Lives

| What | Where |
|---|---|
| Settings (`UserSettings`) | `%AppData%\LetsClip\settings.json`, written through a temporary file flushed to disk and a rename |
| Clip metadata (trim, logical range, recorded time) | `%AppData%\LetsClip\Clips\<hash of path>.json`, ignored when the file's size or write time no longer match |
| WebView2 profile | `%AppData%\LetsClip\WebView2` |
| Replay cache | `%LocalAppData%\LetsClip\Cache\<session guid>\seg_*.ts` and `aud_*.ts` |
| Thumbnails and timeline strips | `%LocalAppData%\LetsClip\Thumbnails`, deleted with the clip's metadata when the library's watcher sees the clip deleted, in the app or in Explorer |
| Logs | `Documents\LetsClip\Logs`, one file a day, the newest 30 kept (`maxArchiveFiles`) |
| Saved clips | `Videos\LetsClip` (the Videos known folder) or the folder picked in Settings |
| Exports | `<clips folder>\Exports` |
| Start with Windows | `HKCU\...\Run` value `LetsClip` with `--tray`, and `Start Menu\Programs\01 Apps\LetsClip.lnk`, both rewritten on every Release launch |

A Debug build uses `LetsClip Debug` for all of these (`AppInfo.FolderName`) and never registers with Windows. `LETSCLIP_ROOT` moves every one of them under a scratch folder, gives the app its own single instance handle and skips the registration, for tests.

## Automatic Buffering

- Buffering has one saved switch, Settings → Buffering → Buffer in Background (`UserSettings.Buffering`, on by default, the owner's pick: no first run notice, its privacy words sit in the switch's info icon). The tray's Turn Buffering Off/On and the panel's Start Buffering (shown only while it is off) flip the same switch, so it lasts past a restart. An old settings file whose notice was answered No starts with it off. While it is on, `CaptureController` starts buffering at launch, after an unlock, a wake, the display coming back and a monitor returning; the panel shows Try Again after an error, and turning the switch off clears an old error.
- `CaptureHolds` (locked, asleep, display off, exiting) stop it and clear the history; it starts again only when no hold is left. Displays that sleep after the Windows timeout count, so an app left alone stops buffering on its own. Exit is a hold, never the switch.
- A saved monitor that is unplugged falls back to the primary, so buffering never sits idle without a word; it moves back when the monitor returns. `CaptureController.DisplaysChangedAsync` names what happened to the running monitor (disconnected, or its display settings changed) and restarts only what differs. 30 FPS is always offered, even on a 24 Hz screen.
- A start that throws anything (a timed out encoder test, a blocked FFmpeg, an unwritable cache) ends on Error, never stuck on Starting. A failed encoder test is tried again at the next start; only passes are cached (`VideoEncoders.WorksAsync`).
- `ReplayRecorder` raises `StatusChanged` only when the status really changes, and its health check ticks only while a session runs: the tray and an open page no longer wake every second.
- Games Only records the game's own window, never the desktop: alt tab, chats and notifications stay out of the clip. `GameWatcher` scans the running processes every two seconds for a known game with a window on screen (not minimised), so a game started before LetsClip is found too, and counts it until its process exits, read from that one process's handle without listing processes again. It scans only while Games Only and buffering are on and nothing holds capture. Known games are `GameScanner`'s Steam, Epic, Riot, Rockstar and Roblox libraries plus `Games` folders on C, D and E, with `UserSettings.AddedGames` added and `RemovedGames` taken out (`CaptureController.GameList`). Turning Games Only on or off stops the capture and starts the other source.
- Settings → Games Only → the blue N Games link opens `GamesDialog`, a bordered table: the red X keeps the key in `RemovedGames`, so the game stays greyed at the bottom with Add Back. Add Game is a menu of the apps open right now (`GameWatcher.RunningApps`, Windows' own hosts and WebView2 left out, read when the dialog opens) plus Browse for an Exe; both key the game by `GameScanner.NormalizeProcessKey` of its process and name it by its product name (`GameWatcher.GameOf`).
- Every ask (a setting, the page, the tray, Windows events, the game watcher, a dropped capture) runs `CaptureController.StepAsync` alone under one semaphore: it applies its change, works out the wanted `CaptureOptions` (null while off, held or with no game) and restarts only when that differs from the running session's `ReplayRecorder.Options`. Nine quick clicks on the capture panel restarted once, with the last values; 40 setting and switch changes from several threads at once ended on one FFmpeg pair and one cache folder with the last values, and switching off left neither. Settings are written inside the controller's lock, so quick changes land on disk in order.
- A stop for a restart, a hold or exit first lets a running save finish (`WaitForSavesAsync`, 5 s at most), so a clip saved just before a switch keeps its whole length. A press while capture restarts says "Capture is starting, try again in a moment".
- Restarts stay out of sight: the chip and the tray read Buffering throughout (`CaptureController.ShowsBuffering`, `StatusText`) and the Save button stays enabled, never Starting or Stopping. Switched off, the chip reads Buffering Off in amber.
- First start defaults are buffering on, 30 s, 1080p, 30 FPS and Normal quality (`UserSettings`).
- A session that ran 30 s or more and then dropped (the encoder exited, a game recreated its window) starts over by itself 3 s later (`ReplayRecorder.Dropped`); a capture that fails to start stays on its error. The reason names the exit code.

## Capture

- Monitors: `ddagrab` (Desktop Duplication) on the adapter and output that `MonitorCatalog` finds for the saved monitor's device path, never a stored index. The frame comes back unrotated: rotation 90 is `transpose=clock`, 270 `transpose=cclock`, 180 both flips (checked on the portrait LS27AG500N at 270).
- Game windows: `gfxcapture` (Windows Graphics Capture) on the window handle `GameWatcher.GameWindow` reads fresh at each start, with no yellow border, sized on the GPU to the output box of the monitor holding the window (`MonitorCatalog.MonitorOf`, `resize_mode=scale_aspect`, so a windowed game gets bars). It sends a frame only when the window changes, so keyframes are forced each second of time (`-force_key_frames`), and the video stall check and slow frame rate warning are off for it: a minimised game sends nothing and only its exit ends the session. A window that is completely still from its first moment cannot start: the encoders hold their first frames until more arrive, so no segment ever closes (a still test window failed every encoder after 12 s each). Games and apps that draw anything start fine.
- Resolution is a select of `UserSettings.ResolutionChoices` (480p, 720p, 1080p, 1440p, 2160p) below the picked monitor's short side plus the monitor's own size, labelled by that side (`CaptureController.ResolutionChoices`). A choice fits its 16 by 9 box in the monitor's orientation, never up (`ReplayRecorder.OutputSize`, 480p is 854 x 480); one at or above the short side is the monitor's own size. The saved value is the picked lines (`UserSettings.Resolution`, 1080 by default), and a monitor without it takes the nearest below, like frame rates. An old `FullResolution` on becomes 2160. Frame rates are `UserSettings.FrameRateChoices` up to the monitor's refresh rate, which `MonitorCatalog.RefreshRateOf` reads with `EnumDisplaySettingsW` into a raw `DEVMODE` (`dmDisplayFrequency` at byte 184).
- `hwdownload`, then one CPU `scale` with BT.709 limited range, then `nv12`. Measured with the window shown: 2560 x 1440 to 1080p at 60 FPS takes about half of one CPU core for the video process, 2560 x 1440 native at 240 FPS about two cores and 606 MB, holding 240 FPS (7198 frames in a 30 s clip).
- Intel Quick Sync converts on the GPU instead (`VideoEncoders.QuickSyncGpu`, `GpuFrames`): `hwmap=derive_device=qsv`, then `vpp_qsv` sizes, turns (`transpose` clock, cclock, reversal) and makes `nv12` with BT.709 limited range. Measured in November 2026 on an i5-1335U with Iris Xe and FFmpeg 9.0.2: Desktop Duplication at 1080p60 takes 21% of a core against 83% on the CPU route, window capture 4.8 against 13.9 ms of CPU per frame, both holding the rate (10,798 frames in 3 minutes with a build running); colour bars score 43.9 dB for the conversion alone (CPU `scale` 42.6) and 48.6 after encoding (45.1), limited range on both. Downscaling 1440p to 1080p is softer (40 to 42 dB against Lanczos in every `scale_mode`, CPU bilinear 44.3), so only a monitor above 1080p recorded at 1080p differs. A failed GPU start falls back to the CPU route on the same encoder without a warning. `scale_d3d11` fails on Iris Xe too (`E_INVALIDARG`); AMD and NVIDIA keep the CPU route, NVENC untested.
- No GPU-only route works on the RX 9070 XT with FFmpeg 9.0.2, all retried in November 2026: D3D11 frames straight into `h264_amf` fail in `SubmitInput` (error 18, DirectX failed), `scale_d3d11` cannot create its NV12 texture (`E_INVALIDARG`), `vpp_amf` fails `AMFConverter-Init` (error 10) whatever its colour options, `hwmap` to AMF is not implemented, Vulkan mapping is not implemented for D3D11, and `vsrc_amf` rejects 240 FPS while its frames fail encoder init at lower rates. Downloaded BGRA fed to AMF halves the CPU at 240 FPS (0.84 cores against 1.70), but AMF's own conversion scored 36.6 dB on colour bars against 44.6 dB for the `scale` above, and its range follows the input's tags (full range from `ddagrab`), so it is not used. `fast_bilinear` saves no CPU per frame and drops to 39.6 dB. Colour checks use known bars, never the live screen, whose frames already differ at 24 dB.
- The encoder is the first that really encodes a few test frames (`VideoEncoders.WorksAsync`): AMF, NVENC or Quick Sync for each GPU vendor present, then x264. A one second GOP, no B frames, and `h264_metadata` writes the BT.709 colour description the hardware encoders leave out. Rates grow with the pixel rate: load is the square root of pixels per second over 1080p60, at least the frame's own share of 1080p (1 from 1080p up, 0.67 at 720p, 0.44 at 480p), the average 20 Mbps and the peak 40 Mbps times the load. Only AMF and x264 are tested on this PC.
- Quality is Normal, High or Max (`CaptureQuality`, Normal by default): High gives 1.75 and Max 2.5 times the average and peak bits, with quality level 22, 19 or 16 for QVBR, NVENC's CQ, Quick Sync and x264's CRF (`VideoEncoders.TuningOf`); the replay cache grows with the peak.
- One second MPEG-TS segments from the `segment` muxer, each listed on standard output as `name,start,end`, with `mpegts_copyts=1` so the files keep the media clock. `SegmentCache` keeps the replay length plus three seconds, within 1.5 GB or the replay length at the peak rate plus 20%, whichever is larger, and never evicts past a pinned save.
- Audio runs in a second FFmpeg process. In one process the scheduler held the live video back whenever the piped audio lagged the video by 100 ms, and capture fell to 6 FPS; apart, both run free.
- `FFmpeg.Start` opts every child out of power throttling (`SetProcessInformation`, execution speed and timer resolution). Windows throttles the children of an app whose window is shown, even when covered, and capture fell to 35 to 45 FPS whenever the LetsClip window was open; hidden to the tray it was always 60. A sibling FFmpeg started outside LetsClip never slowed, which is how it was found.
- The media clock: `AudioMixer` places each WASAPI packet at its QPC time (sample zero is the session's start, media time 1.0), silence and gaps stay silence, and a packet within 20 ms of the last one continues it. Video gets onto the same clock with one wall clock reading at its first frame (`setpts` with `RTCTIME`). Both clocks are read in microseconds.
- The audio process shifts its output with `-output_ts_offset`: FFmpeg 9.0.2 ignores `-itsoffset` on the raw `f32le` pipe, which left v1.2's audio on a clock one lead second early, so every clip played its sound about 0.94 s before the picture (measured with a flashing window and a 20 ms WASAPI beep). Since the fix the beep lands 11 to 54 ms after the flash over ten beeps.
- A save pins the cache, waits for the segment holding the key press to close, joins the segments with the `concat:` protocol and stream copies them up to the press into an MP4 named `LetsClip yyyy-MM-dd HH-mm-ss.mp4` (`ClipNames`). Both inputs are shifted so the replay's start is zero (`ClipSaver`, `-itsoffset` minus the start, no `-avoid_negative_ts`); the keyframe pre-roll before it lands below zero, where the MP4 edit list hides it, so a 30 s replay plays, probes and exports as 30 s (30.00 to 30.03 s measured, 900 frames at 30 FPS). WebView2 and FFmpeg both honour it: a clip whose hidden pre-roll is red shows no red frame in the editor, and an export from it matches the source at 44.5 dB against 19 dB half a second off. A session younger than the replay starts at its first sample instead (media time 1.0). It runs off the UI thread and returns before any thumbnail is made (the library makes it later). A monitor save took 1.5 to 2.2 s from press to file on the i5.
- A still game window sends no frames, so its segment never closed and a save waited out the 8 s stall timeout (9 s for a Claude window). Window sessions write their video segments with `flush_packets=1`; after 1.5 s the save joins the open segment (the newest `seg_` file) as it stands on disk, its last frame holding to the press while the audio runs on, shifted to the replay's start with `-itsoffset` when it is older than that. At most the encoder's last few held frames are missing. Measured on the i5: 2.2 s from press to file, for a window still 10 s (moving video, then its last frame) and still 40 s (one frame, 30 s of sound).
- Quick Sync ignored the forced keyframes as split points until `-forced_idr 1` (AMF and NVENC already force IDR): a game window's segments then closed only every 60 encoded frames, or never while still, which is what made that 9 s save.
- A clips folder on a drive that is gone saves to `Videos\LetsClip` instead, so the replay is kept, and the balloon then shows that file in Explorer (folders compare through `FilePaths.AreSame`, case and a trailing slash aside); save errors read as plain words (`ReplayRecorder.SaveErrorOf`). `ClipMetadata.FrameRate` keeps the capture rate, which exports prefer over a window clip's low probed average.
- A save plays `SaveChime` (two soft bell notes a fifth apart, a third of a second, played by `PlaySoundW` from a pinned buffer so any thread can call it; `SoundPlayer` raced on two quick saves) instead of the Windows sound, when Save Sound is on, the moment the save is accepted (`ReplayRecorder.SaveStarted`), not when the file is written; the balloon still waits for `ClipSaved`; `SaveChime.Play` first has `AudioMixer.MuteSystemAudio` write the loopback as silence for that long, so the chime never lands in the next clip. Settings plays it from the speaker button beside the switch. The tray balloon is silent: `TrayBalloon` sends `NIIF_NOSOUND` through `Shell_NotifyIconW`, borrowing `NotifyIcon`'s private `_window` and `_id`.
- Lock, sleep, display off, a monitor change and a stalled encoder all end the session and clear its history; nothing splices across them.

## Export

- Re-encodes the trimmed range from the saved clip at 1080p at most (no resolution choice, the owner's pick): `-ss` before `-i` (frame accurate when transcoding), `scale` plus `pad` to even sizes, `yuv420p`, BT.709 tags, AAC 128 kbps, `faststart`.
- The ceiling is the size past which an export gains nothing (`SizeBudget.CeilingMegabytes`): Sharp twice over at the output size, frame rate and audio (0.09 bits per pixel, a slow clip counted at 30 frames since each of its frames changes more), or half again the selection's share of the source file when that is smaller, never below twice the video floor or 2 MB. A 5.5 MB still clip once offered up to 47 MB; it now needs 9 MB. `ClipExporter` clamps every request to it, capped at 4000 MB, since 4000 MB failed in FFmpeg with Result Too Large.
- Size Limit is a select of fixed limits (`SizeBudget.Limits`, 20, 50, 100, 200 and 500 MB) offered only below the ceiling and where the export can still meet them, then Unlimited (4000 MB, so the ceiling decides) (`SizeBudget.LimitsFor`). With nothing below the ceiling the row is gone and the export aims at the ceiling. The pick is saved as picked (`ExportMegabytes`, 20 MB by default): a saved limit at or above an export's ceiling means Unlimited for it, else the nearest offered below, else the smallest offered. Its info icon says what the limit and Unlimited do, without naming any app.
- The verdict reads Sharp whenever the target holds the selection's own bytes (`keepsSource`), whatever the bits per pixel, since a re-encode cannot find detail its source never had; otherwise the bit rates below decide. The bitrate line says Up to, since still scenes come out smaller.
- Frame Rate is 60 FPS or the clip's own when it runs above 60 (`ExportFullFrameRate`, `ClipExporter.FrameRateOf`); a 240 FPS clip at 10 MB is otherwise Too Small.
- `SizeBudget` turns the limit (decimal MB) into a video bitrate after a 5% margin, the MP4 index and audio. Bits per pixel decide Sharp, Good, Soft or Too Small; Too Small refuses.
- The hardware encoder goes first (single pass VBR aimed at 90% of the budget, since AMF overshoots), x264 two pass second. Every result is probed and its real size checked; over the limit retries at a lower bitrate, twice per encoder. An export is named by its clip, never by its limit (`LetsClip 05-11-2026 8h30`, then `(2)`). Cancelling mid-encode once reported "Export failed, the file could not be written" and left the partial file: the killed encoder's file stays locked a moment, so `FFmpeg.DeleteOutputAsync` retries for two seconds and never replaces the real outcome. On a 30 second noise heavy 1080p60 test AMF landed 18.4 MB for 20 MB and 9.3 MB for 10 MB on the first try in about 9 s, and scored VMAF 85 against x264 two pass 74 at the same size (28 s). A 12 s 1080p120 test pattern landed 8.7 MB for 10 MB at 60 FPS.

## Updates

`Updater.CheckAsync` reads the `releases/latest` redirect without following it, so it needs no token. It runs on every start (no setting) and from **More (⋮) → Check for Updates**; a newer version opens `UpdateDialog` and a red dot stays until restart: a `MudBadge` on the More menu (`d-flex`, or it lifted the button 2 px), then `update-dot` on Check for Updates. What Changed shows the release body's lines (`AppInfo.ReleaseApiUrl`); an empty body hides the list.

Update Now hides the X and Escape until the download fails (`UpdateDialog.SetClosableAsync`). `Updater.DownloadAsync` saves the new exe beside the running one through a `.download` file that must match the asset's SHA-256 `digest`; a mismatch or missing digest opens the release page instead. `Updater.Launch` starts it with `--after-update <pid>` and the window exits through `MainWindow.ExitAsync`, finishing saves. The new exe runs `Updater.FinishPreviousVersion` before the single-instance check: it waits up to 60 s for the old process (which may finish a save for up to 15 s first) and deletes every other `LetsClip_v*.exe` beside it. A protected folder, a Debug build or a renamed exe (`Updater.CanInstall`) opens the release page. Build with `-p:Version=0.9` to see the dialog.

## Text

- Labels are short Title Case, and inside one the short joining words stay lower case, the owner's pick: a, an, the, and, or, as, at, by, for, in, of, on, per, to, with (Start with Windows, Show in Folder). The first and last word keep their capital. Comments keep every word capitalised, RazorStyle checks that.
- Longer sentences (descriptions, hints, warnings, snackbars) are sentence case, short, and never end in a symbol; with two sentences only the last goes without a full stop.
- A field or section that needs explaining gets a tonal blue `InfoIcon` in a tooltip, never a caption (`SettingRow` takes it as `Info`).
- Every alert is a `Notice` (dense, raised, rounded, warnings in their own colour), and one CSS rule sets its text to the body2 size of the text around it.
- A value about a choice sits greyed (`mud-text-secondary`) on the right where the row has room, never in brackets: a monitor's size and refresh rate in its select item, Default beside the Windows default audio device (`AudioDeviceInfo.IsDefault`), the clips folder, the export size. Device names drop their endpoint (Headphones), unless two devices would then share a name.
- Settings and panel rows are a title and their control, no description under them (the owner's pick); the capture and export panels use the same `SettingRow`. The status chip in the app bar is a plain chip, no tooltip or click, and names the game it records (Buffering Overwatch); switched off it reads Buffering Off in amber. Every panel holds its content 24 px from its edge (`px-6`), cards 16 px (`pa-4`).
- No full path on screen: the clips folder shows relative to the profile (`Videos\LetsClip`), and the empty Clips page says only No Clips.
- No app is named: exports are ready to share, copied files paste anywhere, and the drag handle drags to another app.
- The monitor overlay names a monitor as `Display 1: 1920 × 1080` (`MonitorInfo.Label`), the same words the logs use.
- Numbers follow the Windows format (`Formatter` uses the current culture). Every shown date goes through `Formatter.FormatDateTime`: `dd-MM-yyyy`, then the hour and minute without leading zeros and a zero minute left out (`05-11-2026 8h30`, `8h5`, `8h`). Every shown time and length goes through `Formatter.FormatDuration`, zero parts left out (`8m30,5s`, `1m`, `0s`), the player clock and replay lengths too. Saved clips keep the sortable `yyyy-MM-dd HH-mm-ss` file name; an export of one is named by its shown date (`LetsClip 05-11-2026 8h30`). A clip still under its generated name shows its date as its title, also while the editor loads; a renamed file shows its name.
- A link that carries on from the value above it starts lower case (or Record a Monitor), the owner's pick. The Save button names the hotkey on a second line (or Ctrl+Shift+F8), hidden while the hotkey is not registered.
- A hotkey another app holds is said in a balloon at startup too, since a tray start shows no panel. Picking new keys in Settings ends when the window hides or the page closes (`letsClip.cancelCapture`), so the saved hotkey always comes back and no key is swallowed later.

## Layout

- The editor fills the window and ends `--page-bottom` above it (`page-fill`, `fill`, `fill-column`); a dialog table scrolls under its fixed header (`.mud-table.fit` with a `max-height`).
- Clip cards sit straight on the page in a `MudGrid Spacing="3"`, never inside a panel. Card actions always show, never only on hover.
- Inputs never stretch with the window: a select sits in a `MudElement` with `fixed-width` (`wide` for device names), because `MudSelect` puts `Class` and `Style` on an inner element.
- Buttons are never outlined: filled for actions, text for quiet ones. Only the capture panel's full width button keeps its icon at the left edge with the text centred (`icon-left`); everywhere else icon and text centre together, the owner's pick. A choice of two or three is a `MudButtonGroup` (`OverrideStyles` false) of small filled buttons, `Color.Info` when picked; more choices are a select (the six frame rates overflowed the capture panel), and so is any list whose length follows the monitor or the clip (frame rates, resolutions, size limits), so the control never changes kind. No ripple.
- A button that cannot do anything is disabled, and a disabled control gets no tooltip: `Tooltip` takes `Disabled` with the same condition. Every tooltip is the `Tooltip` component, never a native `title`.
- A dialog closes with its X only, and its action says what it does (Add Game, Update Now). `ConfirmDialog` keeps Yes and No.
- Sliders get a real 16 px thumb, a rounded filled track and a focus ring in CSS: MudBlazor scales a 2 px circle, lopsided at 125%.
- The player shows the clip at its own shape, centred, with the inner radius and the panel shadow, never a frame or black bars beside it. Its controls are one row of icon buttons in tooltips (time left, transport centred, reset trim, mute and full screen right), the trim values sit under the timeline, and there is no hint text. The 5 second jumps are the plain Replay arrow, mirrored for forward (`mirror`). Hovering mute raises a vertical `MudSlider` for the volume; MudBlazor only rotates it, so CSS centres it at a fixed length, and sliding to zero mutes. A spinner holds the player's place and every control stays disabled until the first frame loads (`OnPlayerReady` on `loadeddata`). The player loop runs only while the clip plays or until a seek is drawn and reported (`kick` on play, pause, seeking and seeked): left running on a paused clip it kept WebView2 at about 7.6% of a core against 0.9%. Its ten time reports a second render only `PlayerClock`; the editor renders when play or pause flips (every report re-rendered the whole editor and export panel before, 57% against 46% of a core in Debug while playing). Full screen hands the video to the browser's own controls, `MainWindow` takes the whole monitor while `ContainsFullScreenElement` holds, and Escape or a double click leaves.
- Clips delete to the Recycle Bin after a question (`Explorer.Recycle`), from the card's red bin or the editor's header; the editor lets go of the file first. Removals are red always, never only on hover. ## Looks Wrong, Is Not

- Each capture writes two segment streams (`seg_` video, `aud_` audio); the save joins them by their shared timestamps.
- `ClipSaver` writes the clip as `.LetsClip-<guid>.mp4` and renames it only after it probes back; such leftovers after a crash are ignored by the library and never deleted, since the clips folder belongs to the user.
- `CacheFolders.Delete` refuses anything but a GUID folder directly under the cache root and only deletes files named like segments or x264 pass logs.
- The preview is muted while buffering: unmuted, its sound would land in the next clip.
- Leaving the editor cancels a running export. Exiting leaves a running export to the kill-on-close job, like a crash.
- The tray balloon can open another clip into the open editor: each loaded clip has its own lifetime (`_lifetime` token, its own `DotNetObjectReference` let go on detach, its pending trim written when it ends), so a probe or timeline strip still running for the last clip never lands on the next, and `ExportPanel` is keyed by the clip's path, so an export or a pick never carries over.
- A saved clip holds up to a second of keyframe pre-roll below zero behind its MP4 edit list: `ffprobe -show_packets` lists it with negative times and the discard flag, players never show it.
- A capture's FFmpeg is disposed only after its exit code is read (`SegmentProcess.Exited` always completes), so `ReplayRecorder.WatchEndAsync` never waits forever; `GameWatcher` reads and lets go of the found game's handle under one lock.
- A still game window's clip can end its video before its audio: the last frame holds while the sound runs on to the press.
- A warm-up clip's file starts with about a second of audio before the first video frame, and that first frame can show content older than its timestamp (`ddagrab` probes it at start); thumbnails come from a second in.
- The video FFmpeg holds about 600 MB of private memory, flat over a 10 minute run; the audio one about 23 MB.
- Opening the monitor list shows a `MonitorOverlay` on every monitor (accent edge and name on the picked one, grey on the others), and a pick stays outlined 1.5 s. The overlays are click through, never activate and carry `WDA_EXCLUDEFROMCAPTURE`, so a screen grab or a clip never shows them even while buffering.
- The playhead draws above the trim handles at full height, so it never thins to half its width at the start or end; each handle's grip line is 3 px, centred by layout so it snaps to whole pixels.
- The trim handles sit outside the kept part, their inner edge on the time, so two handles never cross or overlap; the timeline pads both ends by a handle's width (`--handle-width`) and maps time over the inner `timeline-track`. Dragging and arrow keys run in `AppShell.js`: it reads the range from the handles' `data-time`, paints handles, shades and selection itself, seeks the video, and tells Blazor once (`OnRange`) when a drag ends or a key steps, so no frame waits on a render. Blazor's next render matches what the script painted.
- Play runs from the playhead and stops at the end point, starting over from the start point once there; the 5 second jumps clear that stop when they pass it.
- The timeline strip decodes keyframes only, one a second, so it samples 12 frames over the duration less one second; spread over the whole clip, the last tile of a short one stayed black.
- A clip with no metadata reads its recording time from its generated name (`ClipNames.DateOf`), so a copied file keeps its date.
- WebView2's browser keys, zoom and pinch zoom are off (`AreBrowserAcceleratorKeysEnabled`, `IsZoomControlEnabled`, `IsPinchZoomEnabled`).
