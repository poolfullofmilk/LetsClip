### Capture: The Sweep And The Owner's Picks

The owner asked for a sweep of the whole project, tested for stability in real life scenarios, and picked from its list of 18: a game window Windows can record (1), kept replays (2), free space for a replay in memory (3), FFmpeg's pipe handles (4), Record during a save (5), one clip for a hammered key (7), the replay outside the .NET heap (8), the Clips page with many clips (9), thumbnails four at a time (10), replay length per game (16), the duplicated recorder code (17) and the docs' drift (18); then from ideas A to J a standard test pass (F), leaner docs (G), the biggest files split (H) and a window's capture kept through its monitor's mode change (I).

- Found in his log of 17 November 2026: Roblox reopened and `GameWatcher` kept the window .NET reported as its main one, which Windows Graphics Capture refused with `0x80070057` fifteen times in 2.5 minutes, backing off to a minute and showing Recording Error. Stand-in windows showed the cause: a destroyed window gives that error, and cloaked, zero sized, transparent, minimised and excluded windows give no frames at all. The game's window is now its largest visible, unowned, uncloaked one, a refused window is passed over within 2 s without counting toward the backoff, and a new main window moves capture to it. Measured: windows that blinked in and out for 12 s were tried nine times, never escalated, and the steady one recorded 3 s after it appeared; a cloaked one never recorded.
- Kept replays: a game closing, a crash or a restart cleared the replay at once, so a press right after a crash saved nothing. Now the ended session's replay is kept for its own length: the closed game's 19 s saved in 0.1 s, a window made anew gave two clips (24 s kept, 4.1 s new), an encoder killed mid session gave both, and a lock still cleared it (no Save button, nothing saved).
- The replay outside the heap: each segment cost two large object heap arrays a second (a `MemoryStream` and its copy), about 8 MB a second at 28 Mbps, which brought a full collection every 26 s, 118 MB of a 233 MB heap fragmented, and 760 to 834 MB private at Max. With `SegmentBuffer` over native memory a 30 minute soak (a save every 2.5 minutes, the editor every third, a two minute Record) had one full collection, as the Record started, the heap 129 to 162 MB, native memory 92 MB for a minute at 1080p60 Normal (154 MB at 1m47s of Record), private 464 to 524 MB with the window open, handles 1904 to 1977; the 2m0.6s Record (178.7 MB) saved in 0.9 s.
- Free space: a start needed 2 GB plus the whole replay free on the cache drive, and a session stopped under 1 GB free, while the replay sat in memory. Only the part past the memory budget counts now.
- Pipe handles: a run's redirected readers stayed open until a collection, about three handles each, and a sandbox sat at 5,770 handles after 2,000 runs. They are released once read (`FFmpeg.Release`).

### Capture: Round 3

The owner's picks from the improvement list of that afternoon, built while he played and finished while he was away.

- The replay lives in memory. Each FFmpeg keeps its segment muxer but writes every one second segment into a named pipe of its own (`//./pipe/LetsClip-<session>-seg_%06d.ts`), which a dedicated thread reads with blocking reads (`CaptureSession.SegmentProcess.ReceiveSegments`); the segment list on standard output still marks each finished segment, and the bytes wait for it (`ReceivedOf`). Eight pipes wait ahead of FFmpeg, each with 8 MB of buffer, so a slow moment in LetsClip never blocks its writes. The thread is its own on purpose: on .NET 11 an async pipe read completes on the shared thread pool, which a busy moment could hold up, the owner's rule of reliability over lightness. Pipes take only this user (`CurrentUserOnly`) and never a name someone took first (`FirstPipeInstance`). A stop closes the waiting pipes and connects to the one the thread waits on, which wakes it (`ClosePipes`).
- Past a gigabyte, or a sixteenth of the PC's memory, the oldest segments are written to the session folder and dropped from memory (`SegmentCache.OverMemory`, `Segment.Spill`): the file is whole before memory lets go, so a save reading at that moment finds one or the other. Evicted segments delete their file only when they had one. A spill that fails keeps the segment in memory; the existing check stops the session before the disk fills.
- Saves stream the segments into the remux through two more pipes, video and audio (`ClipSaver.RemuxAsync`, `FeedAsync`), from memory or the spilled files, so a long Record needs no joined copy and no command line listing segments. - A RAM ring instead of disk segments (as Medal says it does) would spare about 9 GB of writes per hour of gaming at 20 Mbps, which a consumer SSD rated for 600 TB takes for decades, so the disk stays.
- FFmpeg against other engines (searched on 9 November 2026): every recorder uses the same NVENC, AMF and Quick Sync hardware, so the encoding itself is equal; what differs is keeping frames on the GPU. Media Foundation is not consistent across vendors (a 2026 benchmark found NVIDIA's current driver registers no H.264 encode transform), OBS's libobs brings a whole compositing engine, and the vendor SDKs mean three native integrations with their own driver quirks, which is what FFmpeg absorbs. The one gap left is the frame readback on AMD and NVIDIA (see Capture); `scale_d3d11`'s bind flag question was still open on the FFmpeg list in June 2025. NVENC can take `ddagrab`'s D3D11 frames directly when no scaling is needed, untested for want of an NVIDIA card.

Tools, all throwaway and never committed: a Release publish with temporary `TIMING` lines in `App.Start` run three times in a `--tray` sandbox and twice shown; a file-based app timing `WScript.Shell`'s shortcut save to a scratch path; one repeating `ClipSaver`'s copy and probe on 33 noisy x264 segments; Defender's `% Processor Time` counter while a test FFmpeg wrote segments; a harness on `CaptureController` with Notepad as the only added app, then monitor mode, in a sandbox; and a Release publish with the sandbox check of `DeleteOldUnpackedVersions` lifted, run beside the owner's running copy, which deleted v1.1.1 to v1.7 and two idle test extractions and kept the running copy's. The second pass added a WinForms test window drawing moving shapes (keyed `pattern`), a harness recording it and the monitor through `CaptureController` with settings passed as a file (PowerShell 5.1 strips the quotes from a JSON argument to a native program), a script running the capture's own FFmpeg chain with one option changed per run and sampling its private memory, CPU and progress frames over 15 s, a harness on the app's own `CaptureSession` with x264, a `Process.GetProcesses` timer, and CDP's `performance` entries for the page.
