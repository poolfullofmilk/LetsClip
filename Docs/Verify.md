# LetsClip, Verify

How each kind of change is checked, the tools that do it and the baseline numbers. Read at step 6 of every round. Part of `CLAUDE.md`, its rules bind the same way.

## Verify

- `dotnet build LetsClip.slnx`, then the analyzer, CSharpier, RazorStyle, line ending and comment checks from the shared rules. The comment check covers `LetsClip.css` and `AppShell.js` too.
- Background cost, measured on the i5-1335U in November 2026 with the Debug build hidden in the tray: idle waiting for a game 0.36% of a core in all, recording a monitor at 1080p60 on the GPU route 19.4% (video FFmpeg 17%, audio FFmpeg 1.5%, LetsClip 1.2%). `AudioMixer` writes 40 ms chunks and sleeps 20 ms between them. The editor's player loop runs only while playing or seeking: left running on a paused clip it held WebView2 at 7.6% of a core.
- Rechecked on 5 November 2026 with the PC busy, Quick Sync on the GPU route: FFmpeg costs follow the frame rate, not the resolution (about 15% at 30 FPS and 40% at 60 FPS from 480p to 1080p, 200 to 300 MB), switched off 0.1 to 0.2%, every setting held its rate (59.2 to 60.0 FPS), and v1.2 measured the same within the noise (alternating runs averaged 35% against 31%). The Release build hidden in the tray took 2.8% for LetsClip and 0.3% for WebView2 while buffering, and held 59.2 FPS hidden and 58.8 FPS shown.
- A 1440p clip at 240 FPS stutters in the editor's preview, since WebView2 cannot hand that many big frames through the composition copy below, and before the count based timing its stamps jumped too. The owner's 30 s 1440p240 Max clip held 6860 of 7200 frames, so that setting is beyond this PC; its export at 60 FPS plays smoothly.
- Performance sweep on 5 November 2026, Ryzen 7 7800X3D (8 cores, 55% busy) and RX 9070 XT with Overwatch running, monitor 2560 x 1440 at 240 Hz recorded at 1080p60 Normal: the video FFmpeg 50 to 58% of one core (capture, download and scale alone 30 to 38%), the audio FFmpeg 2%, LetsClip 0.1%, WebView2 0% with the window open and idle; the GPU's video engine 19% and its 3D engine 2.6% for capture, against Overwatch's 3D 57%. `scale_d3d11` failed on the RX 9070 XT for BGRA too (`E_INVALIDARG`, stock FFmpeg), so the CPU scale stayed; LetsClip's own build converts on the GPU when nothing scales since 14 November 2026 (`Docs/Capture.md`). Discord's GPU process used the video engine as well (8.5%). A hung FFmpeg holding an AMF session made the next start time out and fall back to x264; check for stray `ffmpeg.exe` from tests before measuring.
- Matrix on 6 November 2026, Ryzen 7 7800X3D and RX 9070 XT, 2560 x 1440 at 240 Hz with YouTube playing, AMF, the video FFmpeg in one core's share, each held 30 s then saved and probed: 480p30 21%, 720p60 37%, 1080p30 25%, 1080p60 49 to 61% (Normal, High, Max, no audio, microphone raw or cleaned alike), 1080p120 102%, 1080p144 170%, 1440p60 70%, 1440p144 Max 117%. Each held its rate exactly (no frame held twice), its audio within 20 ms of the video's length, and saved in 1.2 to 1.6 s (2.5 s for a 120 s replay, exactly 7200 frames). 1080p240 reached 205 to 224 FPS and 1440p240 228 FPS, the slow capture warning showing once below 216; that limit is the GPU readback above. Noise Cancellation costs about 2% of a core, the audio FFmpeg 1 to 2%. Window capture of a 1600 x 900 test window took 19% at 60 FPS, 51% at 144 and 74% at 240, following the window's own redraw rate. Waiting for a game costs 0.2 to 0.4% of a core. Exports landed under every limit on AMF's first try in 4 to 8 s (28 s for a 240 FPS export at full rate), and Unlimited stopped at the ceiling. AMF hung twice, only while a failing window capture started and killed an AMF session every 12 s; the stall check moved those exports to x264, and with nothing churning it never hung.
- Playback in the editor costs the LetsClip process itself (28 to 46% of a core in Release, WebView2 63 to 81%): .NET 10's `BlazorWebView` hard codes `WebView2CompositionControl`, which copies every WebView2 frame into WPF, so anything that repaints each frame costs the host. Idle pages stay under 1%. Only the HwndHost `WebView2` would avoid it, which .NET 10's `BlazorWebView` cannot use; see Build, Run And Publish for the measured 9.0.120 host and why it waits for .NET 11.
- Game and Discord audio is checked with copied tone apps, never the owner's: a file-based WinForms window that plays 440 Hz (`pattern.exe`, added as the only game), a file-based tone player published once and copied as `DiscordCanary.exe` (660 Hz) and `outsider.exe` (880 Hz), `System.Media.SoundPlayer` looping a generated 2 s WAV at -26 dBFS (it needs `UseWindowsForms` for `System.Windows.Extensions`). A sandbox records `pattern`, CDP presses Save, and `ffmpeg -ss A -to B -af bandpass=f=F:width_type=h:width=20,astats` reads each band in 8 s windows of the clip. Start the copied Discord after the session to see it joined. The real Discord's tree is followed too, so delete those clips afterwards. Expect the game and Discord near -29 dB and the outsider below -55 dB.
- 63 clips without metadata listed in 6.5 s on first start (probed four at a time, then cached) and in 0.5 s after.
- Debug self tests run on first use of each helper; a failed one fails fast.
- The log is how the owner's reports get answered, so it runs at Debug and says everything once: the start (version, Windows, .NET, threads, the settings as JSON, `Ready N ms After The Process Started`, the installed games found and how long the scan took), the monitors, every setting change as old -> new (`UserSettings.ChangesFrom`), holds and releases, what each step wanted and ran, retries, encoder tests, every FFmpeg command line and exit code with its time (and the start's own time when Windows took 100 ms or more to start it), the capture's FFmpeg warnings (a repeat is counted, every 100th written), saves and exports with sizes and seconds (a save also logs how long it waited for the press's segments, most of its time), clips opened and recycled, and the microphone test. A start, a save and an export came to 36 KB.
- Sweep on 7 November 2026, same PC with the owner's audio playing, 45 minutes of tests: a harness on `CaptureController` with a borderless 1280 x 960 test window on the 165 Hz portrait monitor that draws a 16 bit millisecond barcode (read back per frame, so duplicates, stalls and clock drift show) and plays a -50 dB tone. Window capture at 1080p60 held 59.6 to 59.9 FPS for 19 to 31% of a core, 1790 to 1800 frames per 30 s clip, no duplicate or stall, audio and video lengths equal, content against stamps flat within 9 ms over a 12 minute soak with a save every 2 minutes and an export every 5 (exports during recording never dropped a frame); FFmpeg memory and handles stayed flat (video 533 to 537 MB, about 1700 handles; audio 22 MB). Monitor capture held every rate exactly to 1440p144 (4320 of 4320 frames); 240 FPS reached 215 to 217 FPS, the known readback limit. 60 and 120 s replays came out 60.011 and 120.009 s, saves took 0.8 to 2 s, six presses in 0.75 s saved three clips and refused three. Every export landed under its limit, Unlimited stopped at the ceiling, a cancel left nothing; cuts kept exactly the frames from Start to End and Restore Original gave back the identical file. AMF stalled once on an export while capture also used it; the 15 s guard moved it to x264, and the same export then ran clean three times.
- Real media checks live as throwaway file-based apps: a pattern window that shows a millisecond barcode and a flash plus a 1 kHz beep each second, a capture harness on the Services, and an analyser that reads the barcode and beeps back out of a clip. Last results: every frame decoded, clip end within 20 ms of the key press, audio about 30 ms behind video (plus or minus 5) and steady across 22 s of silence, a trimmed export within 15 ms of its in and out points. Those predate FFmpeg 9.0.2: on 5 November 2026 a flashing corner window with a 20 ms WASAPI beep showed v1.2's audio 0.94 s early, fixed with `-output_ts_offset` (11 to 54 ms behind since). Uneven gaps between flashes keep each beep paired with one flash.
- Count frames per second of a saved clip with the window shown and hidden; both must hold the picked rate.
- The automation is checked from a harness that drives `CaptureController` directly (a game appearing and closing, holds, the switch surviving an unlock, quick setting changes from many threads, a save just before a switch), so nothing takes the foreground. A file-based app (`dotnet run harness.cs` with `#:project` on `LetsClip.Services`, which is enough) gets the FFmpeg folder copied beside it; it must call `SetProcessDpiAwarenessContext` first, or monitors read at their scaled size, set `LETSCLIP_ROOT` before anything touches `AppInfo`, and carry `#:property PublishAot=false` and `#:property JsonSerializerIsReflectionEnabledByDefault=true`, since file-based apps default to AOT rules and `UserSettings.Save` then throws on reflection JSON. NLog writes nowhere until the harness configures it; read that log with `FileShare.ReadWrite`, NLog keeps it open. The matrix harness steps `CaptureController.UpdateSettings` through each setting, waits until `Recorder.Options` matches, samples the FFmpeg processes' `TotalProcessorTime` and `\GPU Engine(*)\Utilization Percentage` for their pids over 10 s, saves through `CaptureController.SaveAsync`, and reads each clip's packet times with `ffprobe -show_entries packet=pts_time`; it then exports a clip at several limits and ranges, with and without sound, through `ClipExporter`. Window capture is tested on a small WinForms file-based app keyed as a game (`pattern`, moving or `still`), never on the owner's apps. `StartupRegistration` is checked in Release without and with `LETSCLIP_ROOT`, removing the Run value and shortcut afterwards.
- `TestClips/` holds three neutral clips from FFmpeg's `testsrc` and `sine`, never a real recording, about 3 MB in all (x264 `-crf 40 -preset veryslow`): `LetsClip 2026-11-06 08-30-35.mp4` (30 s, 1920 x 1080 at 60 FPS, 440 Hz), `LetsClip 2026-11-05 12-16-02.mp4` (30 s portrait, 1080 x 1920 at 60 FPS, 660 Hz, for the editor's sizing) and `LetsClip 2026-11-01 08-42-10.mp4` (2 minutes, 1280 x 720 at 30 FPS, 330 Hz, for `1m30,5s`). The app never reads that folder and the Clips page never shows it: copy them into the sandbox's clips folder (`<LETSCLIP_ROOT>\Videos\LetsClip Debug` for a Debug build), and never point Clips Folder at the repo, since exports and deletes write there. Rename a copy to today's or yesterday's date to see Today and Yesterday.
- Look at the app over CDP: start it with `LETSCLIP_ROOT` set to a scratch folder and `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=9333`; `http://127.0.0.1:9333/json` lists the page. `Emulation.setDeviceMetricsOverride` lasts only while its WebSocket stays open, so size, act and shoot in one session. A `MudSelect` opens only on real `Input.dispatchMouseEvent` presses; its items and buttons take a script `click()`, and so do a `MudMenu`'s activator, its items and a `MudCheckBox`'s input. A text field takes a set `value` plus dispatched `input` and `change` events, and a dispatched `keydown` reaches `OnKeyDown`. `Runtime.evaluate` keeps top level `const` names between calls, so wrap each script in an arrow function called at once or the second call fails as `Uncaught`. A dialog's scrim takes every click. Sweep at `1600 x 845` and `1280 x 680` for anything past its panel or a sideways page scroll, and measure rather than eyeball: the rects of every `.mud-paper`, `.header-row` and `.setting-row`, computed paddings and radii, and each switch's track and thumb against its row's right edge found the 9 px switch inset, the 24 px editor header gap and the zeroed select padding of v1.8. Build a copy with `-p:Version=0.9 -p:BaseOutputPath=<scratch>\` to see the Update dialog without touching `bin`.
- With the displays asleep the display hold keeps a sandboxed app from recording; check capture while someone is at the PC.

## Baselines On The 7800X3D, 10 November 2026

Published exe in a sandbox, RX 9070 XT with AMF, one 2560 x 1440 monitor at 240 Hz, nothing else running. Throwaway tools as in the handoff's appendices plus a WinForms test window redrawn every compositor frame.

- Recording 1080p60 Normal with system audio: the monitor 58.8% of a core for the video FFmpeg before the round and 65.2% after (the moving test window was on screen both times), 587 MB, audio 0.2%, the app 0.1 to 0.2%; the test window (1600 x 900) 31.7% before and 31.6% after, 524 MB. Every clip 1800 of 1800 frames, longest gap 16.7 ms.
- A tray start waiting for a game: 92 MB private with the hidden WPF window that carried the hotkey, 41 MB since `WindowMessages` owns a plain window (handles 1176 against 600). Recording a monitor in the tray, never opened: 36 to 43 MB. A WPF window that was ever shown gives nothing back, so this holds until the first open.
- The managed heap of an idle tray start grows from 4 to 22 MB in two minutes with no generation 0 collection at all: this CPU's cache gives the runtime a large first budget. Information, no setting changes it from inside a single file exe.
- The page release after 10 minutes in the tray now ends with one aggressive compacting collection (`MainWindow.ReleasePageAsync`): 241.5 MB private just before, 94 MB after, where it took the runtime hours by itself.
- The hotkey, the display hold and the first open were checked on the plain window: an injected key press saved a clip in 1.4 s, the display turned off and on logged the hold and the release, and the page showed its cards 0.5 s after the first open. The tray's right click menu was not clicked by a script, check it by hand.
- Windows restarts a crashed LetsClip 5.1 s after the crash (see `Docs/Recovery.md`); a throwaway app measured 4.9 s.
- `FitToScreen` sets the WebView2 zoom only when it differs, it ran on every step of a window drag.

## The Press On The Real Tray App, 11 November 2026

- The hotkey without a key: post `WM_HOTKEY` (`0x0312`, wParam 1) to the sandboxed process's windows whose class starts with `WindowsForms` (the `WindowMessages` window and the tray icon's, which ignores it). Nothing is injected, so no other program sees a key and a game keeps its focus.
- What sounded: a throwaway file-based app on `LetsClip.Services` (for NAudio) reads `AudioMeterInformation.MasterPeakValue` of every session on the default output every 10 ms, refreshing the sessions every 100 ms, and names each program that sounded with its peak and bursts. It works with the owner's own audio playing, where a loopback of the whole output cannot. A program recording the output (LetsClip while it records system audio, Discord) shows the whole mix on its own session.
- What showed: `CopyFromScreen` of the primary screen's bottom right corner 1.5 s after the press, after `SetProcessDPIAware`.
- Results are in `Docs/Capture.md`. v2.0.5 kept v2.0.4's demo and stills, taken that morning: the round changed no page, style or page script.

## The Evening Round, 11 November 2026

- A sweep run with the window on the zoomed second monitor must scale its sizes by `cssVisualViewport.zoom`, or 1264 emulated is really 1404 CSS pixels wide. Run that way the six sizes were clean on Clips, Settings and the editor with a landscape and a portrait clip.
- Window memory: `MoveWindow` from a throwaway PowerShell, `WM_CLOSE` to hide, then the saved `Window` in `settings.json` and `GetWindowRect` after a restart; four restarts in a row came back on the same rectangle. While `WindowPlacement.Apply` runs, `MainWindow.FitToScreen` stays out (`_placing`): it fitted mid placement with WPF's stale size and undid the restored height.
- Player volume: the slider set to 0.3 and mute pressed on one clip, the next clip opened muted at 0.3 and `settings.json` held both.
- Spinners: Save Cut and Restore Original showed theirs within 100 ms of the press on a 248 MB clip, the timeline's showed while a new clip's strip was made, the Save button's while a save ran.
- Ponytail audit over the whole repository: every style class, token, page script export and declared member is named somewhere else, no component is a bare wrapper, no package is spare. Cut: the capture panel's leftover styles (`game-row`, `icon-left`, `button-hint`, `--side-width`, the stretched split), the jump icons and their colours, `SourceChip`'s class parameter, stale build folders. Left alone: four components each subscribe to the controller's events by hand, the usual Blazor way, a shared base class would hide three lines each.

## On The Work Laptop, 12 November 2026

Where the round ran (i5-1335U, Iris Xe, Quick Sync, .NET 11.0.100 from `%LocalAppData%\Microsoft\dotnet11`).

- Two sandboxes at once: give each its own `LETSCLIP_ROOT` and its own `--remote-debugging-port` in `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS` (9333 and 9334 here); they never share a single instance handle. A build needs both stopped, since they run the same Debug exe.
- A long replay test: both sandboxes recording the primary monitor at 1080p60 Normal for 11 minutes, Save pressed over CDP at 5 and 10 minutes, each clip probed for picture and sound length and frame count (`Docs/Capture.md`).
- The number check: a CDP driver setting the editor through ranges, plans and Audio with real presses on the plan select, reading every row, exporting and comparing each file with FFprobe, then pressing Restore Original after any Export and Save, since a shorter selection's Export cuts the clip (`Docs/Export.md`).
- Per frame recorders: a `requestAnimationFrame` loop started in the same evaluation as the press, logging each new state with its time, for spinners (size, button size before and while busy) and for which controls are disabled during a cut or restore (`Docs/Layout.md`).
- CPU: a PowerShell sampler reading `TotalProcessorTime` of the sandbox's LetsClip (its pid file) and of the WebView2 processes whose command line holds the sandbox's folder, over 10 or 20 s (`Docs/Measurements.md`). Playback stops at the end point, so a window measuring playback must start from the clip's start and be shorter than the clip.
- A sweep measures the busy state too: a button's spinner must not change its size, and a menu with a custom activator must open on a real mouse press (`Input.dispatchMouseEvent`), never only on a scripted `click()`.

## On The Gaming PC, 12 November 2026

- The sweep is one Node script over CDP: per state and size it lists a sideways scroll, anything past its panel, wrapped labels, overlapping row children, overlapping panels and text in dots, and shoots 1920 and 1264 wide. Sizes are multiplied by `cssVisualViewport.zoom` (0.9 on the second monitor).
- Waiting on an element from `Runtime.evaluate` must return a boolean: an element returned by value never reads as true.
- A long replay on one sandbox: raise Replay Length live and press Save only once the history is that long, the cache keeps what the shorter length held at the pick.
- A copy's weight is checked by a throwaway that reads `ffprobe -show_entries packet=stream_index,pts_time,size,flags`, weighs like `SizeBudget.CopyBytes` and makes the real `-ss` before `-i`, `-c copy` file beside it for a list of ranges, with and without sound (`Docs/Export.md`).
- Export and Save on a long clip locks the editor until its new strip is made: a script must wait for Restore Original to be enabled before pressing it.
- The window's place is set with `MoveWindow` from a per monitor DPI aware PowerShell and read back with `DwmGetWindowAttribute` 9, the visible frame: `GetWindowRect` includes 8 px of invisible border on the left, right and bottom.
- A script through the session's shell loses backslashes inside a heredoc: write throwaway scripts with the file tool.
- Tests read copies, never the owner's own clips: on 12 November 2026 a benchmark's hung AMF process kept one of his clips open for two hours and his Save Cut failed with the clip may be in use. Copy a clip into the sandbox first, and give every test FFmpeg a time limit.

## Card Menu And Install Round, 13 November 2026

- The second monitor was off, so the sandbox sat on the first at 125%: a window of 1920 x 1080 reads 1522 x 827 CSS pixels with a zoom of 1, so the sweep's emulated sizes need no scaling there.
- Clips with games for the filter: start the sandbox once so it writes each clip's metadata, stop it, then set `Game` (or `Monitor`) in those JSON files; a long name such as The Elder Scrolls V: Skyrim Special Edition checks the chip's dots.
- The install from a download, for real: publish with the next version (`-p:Version=2.0.10`) to a scratch folder, copy the exe into a `Downloads` folder under the repository's parent, back up the owner's `settings.json`, Run key and shortcut through an `explorer.exe`-started `.cmd`, start the exe through `explorer.exe`, then read the install folder, the Run value, each shortcut's target and the log from a probe script started the same way. A sandbox holding F10 makes the real copy log `Failed To Register Hotkey F10`; stop the sandbox, wait 10 s and start the real copy again.
- `Input.dispatchKeyEvent` for Enter needs `text: "\r"` to press a focused button; without it nothing is clicked.

## Own FFmpeg, Names And Install Round, 14 November 2026

- A new FFmpeg build is checked by running every command form LetsClip uses against its folder before anything else (`Docs/FFmpeg.md`, Making A New Build), each under a time limit.
- Saving without touching a key: post `WM_HOTKEY` (0x0312, wParam 1) to the sandbox's own message window, the `WindowsForms` class window of the sandbox's process (`FindWindowEx` over top level and message only windows, matched by process id). The owner's own copy never sees it.
- A sandboxed window never takes focus, so a script's `.blur()` does nothing: commit a typed name by dispatching both `blur` and `focusout` on the input; either alone did not commit it.
- Three tracks: `ffprobe -show_entries stream=index,codec_type:stream_tags=handler_name:stream_disposition=default` on a saved clip lists `Game and Microphone` (default 1), `Game` and `Microphone` (default 0); an export of one track holds exactly one.
- The toast cannot be screenshotted, by design: check its window from a script instead, top most, `WS_EX_TRANSPARENT`, `WS_EX_TOOLWINDOW` and `WS_EX_NOACTIVATE` set and `GetWindowDisplayAffinity` reading `0x11`, over a full screen test window in front.
- Moving the clips folder to another drive without one: `subst X: <scratch folder>` gives a second drive letter, so the move takes the copy path with its progress; remove it with `subst X: /d` from PowerShell, since Git Bash turns `/d` into a path.
- The install, takeover and uninstall run on the real profile only through `explorer.exe`-started `.cmd` files in a folder outside `AppData`, with the owner's Run value, shortcuts, settings, clip details and logs backed up there first and put back after, and his released version installed again at the end. A message box the test raises closes with `WM_COMMAND` carrying its button's control id (2 for the uninstall's OK); `IDOK` itself was ignored.
- Uninstalling keeps the clips, their details and `settings.json`, so a reinstall picks up where it left; check that `%LocalAppData%\Programs\LetsClip`, `%LocalAppData%\LetsClip`, `%AppData%\LetsClip\WebView2` (deleted by a `cmd` after the exit), the logs, the Run value, the shortcuts, the Uninstall key and the unpacked folder are gone.
