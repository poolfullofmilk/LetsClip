# LetsClip, On Every FFmpeg Update

LetsClip ships its own FFmpeg since v2.0.10: `LetsClip.Desktop/FFmpeg/Build-FFmpeg.ps1` builds it from the pinned source in MSYS2 with only what the app runs, every `.patch` beside it applied, and zips it as `ffmpeg.zip`; that zip is the only asset of one GitHub pre-release on this repository, tagged `ffmpeg` and titled FFmpeg since 18 November 2026, which every rebuild replaces in place and `Get-FFmpeg.ps1` downloads and checks by SHA-256. Run everything below whenever that build changes, before anything ships, and write the new result into the file named beside it. Use `-frames:v` runs so no AMF process is ever killed, and wait 10 s after any kill. Part of `CLAUDE.md`, its rules bind the same way.

## Making A New Build

1. In `Build-FFmpeg.ps1` set the new source tarball and its SHA-256 from ffmpeg.org, and the MSYS2 installer's if it moves. The zip and its inner folder are always named `ffmpeg`, whatever the version.
2. Run it from PowerShell (`powershell -ExecutionPolicy Bypass -File LetsClip.Desktop/FFmpeg/Build-FFmpeg.ps1`); it prints each file's DLL imports, which must name only Windows' own DLLs and FFmpeg's. What its lines are for:
   - `--ld=g++` and `-static-libstdc++`: libvpl is C++, so a plain `gcc` link misses its symbols.
   - `pacman -Rdd mingw-w64-x86_64-ffmpeg mingw-w64-x86_64-ffms2`: x264's package pulls in MSYS2's own FFmpeg, whose static `libavutil.a` then links into the shared DLLs.
   - Decoders keep `wrapped_avframe` (every `lavfi` input, the encoder tests) and `pcm_f64le`; the muxer and demuxer are named `pcm_f32le`, not `f32le`.
   - Filters, parsers and bitstream filters are all built, so a filter the app starts to use needs no rebuild.
3. If the patch no longer applies, see whether stock `scale_d3d11` works now (the first row below) and drop the patch if it does.
4. Run every command form LetsClip uses against the new folder (a throwaway Git Bash script in the scratchpad, each run under `timeout 120`): the encoder test for `h264_amf`, `hevc_amf` and `libx264`; a monitor capture on the CPU route and on the GPU route; the audio capture with three tracks from a four channel `f32le` pipe; the save's `concat:` join to MP4 with track names and dispositions; the probe with packets; a thumbnail, the timeline strip and the waveform; the lossless cut; a copy export of one track; exports with `hevc_amf`, `h264_amf` and both x264 passes; the microphone chain. All 18 passed on 9.0.2 on 14 November 2026.
5. Replace the release's asset in place (`gh release upload ffmpeg ffmpeg.zip --clobber`), wait until a download of `releases/download/ffmpeg/ffmpeg.zip` hashes like the local zip (GitHub served the old file for about a minute on 18 November 2026), put the new SHA-256 in `Get-FFmpeg.ps1`, run it into a scratch copy and compare the files with the build's, check that `releases/latest` still points at the app's newest release, then update `LetsClip.Desktop/FFmpeg/README.md` and `THIRD-PARTY-NOTICES.txt`. Should the release ever be gone, make it again with `gh release create ffmpeg ffmpeg.zip --prerelease --title FFmpeg --notes "LetsClip's own slim FFmpeg 9.0.2 build. Get-FFmpeg.ps1 fetches it and checks its SHA-256."`. Since the asset is replaced, a commit older than the build no longer fetches its own FFmpeg: its pinned hash refuses the new zip, which the owner accepted on 18 November 2026.

## The Second Build, 17 November 2026

- The second build (then the pre-release `ffmpeg-9.0.2-letsclip-2`) adds `gfxcapture_lanczos.patch` (a `lanczos` scale mode: the shader `main_ps_lanczos`, its option and the point sampler it needs), `libopus` as an encoder and the Ogg muxer and demuxer. `Build-FFmpeg.ps1` now applies every `.patch` beside it. The shader compiles with `D3DCompile` at `ps_4_0` the way FFmpeg does it, checked before the build with a throwaway reading the header.
- Built at idle priority with four jobs (`OMP_NUM_THREADS=4`, which `nproc` follows) while the owner played; 11.4 MB zipped, 29 MB unpacked, every DLL importing only Windows' and FFmpeg's own.
- New checks for later builds: `gfxcapture` with `scale_mode=lanczos` against the CPU's Lanczos on a still photo (61.4 dB today), and a sound only Opus export reading back with its track name.

## The Third Build, 18 November 2026

- The third build adds `ddagrab_reopen.patch`. Stock `ddagrab` ends the capture on any failed `AcquireNextFrame`, and Desktop Duplication fails with `DXGI_ERROR_ACCESS_LOST` whenever the desktop changes mode on any monitor of the adapter: a dock, another monitor switched off or on or set to another rate, a secure desktop. The patch releases the duplication on `ACCESS_LOST` (from `AcquireNextFrame` or `ReleaseFrame`), repeats the last frame (`dup_frames`) and opens the same output again every 100 ms, quietly, for up to 30 s; an output that now shows another display (`DeviceName`), size or rotation ends the capture at once, as does anything else failing, so LetsClip restarts it with the right monitor as before.
- Built at idle priority with four jobs in about 20 minutes, MSYS2's packages unchanged but dav1d (1.5.4 to 1.5.5); 11.4 MB zipped, 28 MB unpacked, every DLL importing only Windows' and FFmpeg's own; `vsrc_ddagrab.c` compiled without a warning.
- Checked: a plain `ddagrab` capture into AMF (180 of 180 frames), and every command form the app runs, through the sandbox: the encoder test, the monitor capture on the GPU route, the audio capture with three tracks, saves, a 20 s Record, probes with packets, thumbnails, strips, waveforms and the black check, then through the services themselves: the packet listing, a lossless cut and its restore, an Off copy, an Opus sound export and a vertical HEVC export with its loudness pass. The display change itself is in the Checks table above.
- Hosting changed with it, the owner's ask of 18 November 2026: the numbered pre-releases piled up on the Releases page, so the build now lives in the one pre-release `ffmpeg` (title FFmpeg, a one line description) as `ffmpeg.zip`, replaced in place on every rebuild. It was made from the second build's zip with the same SHA-256 and fetched back identically, `ffmpeg-9.0.2-letsclip-1` and `-2` were deleted with their tags, the third build's zip replaced the asset (SHA-256 `30775f93...b32`, inner folder `ffmpeg`) and `Get-FFmpeg.ps1` fetched it into a scratch copy, its ten files identical to the build's; `releases/latest` still pointed at v2.0.17.
