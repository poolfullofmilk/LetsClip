# LetsClip, Capture

How recording starts and stops by itself, and how the two FFmpeg processes capture, time and save. Read before touching `LetsClip.Services/Capture` or `Games`. Part of `CLAUDE.md`, its rules bind the same way.

## Automatic Recording

- Recording has no switch, the owner's pick (a Buffer in Background switch, a first run notice and a tray pause all came and went): `CaptureController` starts it at launch, after an unlock, a wake, the display coming back and a monitor returning, and only Exit ends it. Every word on screen says Recording, never Buffering: the chip and tray read Recording, Recording Overwatch, Waiting for a Game or App, Saving Clip or Not Recording.
- People set it once and forget it, so every failure retries by itself (`ReplayRecorder.Failed`, `CaptureController.RetryAsync`): 2 s, then 5, 15 and 30 s, then each minute, a failed start and a dropped session alike; the count starts over only when a session had run 30 s, so a capture that starts and dies at once keeps backing off. Any exception a start throws ends on Error and retries, a COM error from a restarting audio service too, never stuck on Starting. Retries stay out of sight, the owner's rule (see Recovery): `CaptureController.ShowsError` stays false for the first four failures in a row (`QuietFailures`, about a minute), so the chip, tray and Save button read Recording and a press waits for the restart. Only a failure that lasts past that, or one the person must fix (`CaptureBlockedException`: HDR on, too little free space for the replay, FFmpeg missing, the monitor gone), shows the error with Try Again, while the retries go on (HDR turned off or space freed starts recording within the minute). Killing the video FFmpeg of a running session restarted it 5 s later with the chip on Recording throughout. A closed game ends its window capture before `GameWatcher` notices (up to 2 s), so a window session whose window is gone (`MonitorCatalog.ClientSizeOf` null) ends quietly too, logged as Stopped Recording, The Window Closed: a game closed 5 s into its session went from Recording to Waiting for a Game or App in 0.8 s, where it used to flash Recording Error; a game that recreates its window restarts the same way.
- `CaptureHolds` (locked, asleep, display off, exiting) stop it and clear the history; it starts again only when no hold is left. Displays that sleep after the Windows timeout count, so an app left alone stops recording on its own.
- A saved monitor that is unplugged falls back to the primary, so recording never sits idle without a word; it moves back when the monitor returns. `CaptureController.DisplaysChangedAsync` names what happened to the running monitor (disconnected, or its display settings changed) and restarts only what differs. 30 FPS is always offered, even on a 24 Hz screen.
- A start that throws anything (a blocked FFmpeg, an unwritable cache) ends on Error, never stuck on Starting. An encoder test that fails or hangs past 20 s counts as failed and the next encoder takes over, with the warning naming it; it is tried again at the next start, and only passes are cached (`VideoEncoders.WorksAsync`). AMF sometimes hangs at init right after another AMF process was killed: seen twice in the November 2026 sweep, where a hung test once left the 1440p144 start on Error. A hardware encoder's capture gets two starts before the next encoder takes over, so one hang does not leave a session on the CPU. Falling back shows nothing any more, the owner's pick after `Using x264 on the CPU, AMD AMF failed` worried them: the clip is fine, only the CPU works harder, and `ReplayRecorder.UpgradeAsync` moves back by itself (see Recovery). A timed out start logs which half went quiet (`Capture Start Waited`, frames and first segments), since the one real case left no other clue.
- `ReplayRecorder` raises `StatusChanged` only when the status really changes, and its health check ticks only while a session runs: the tray and an open page no longer wake every second.
- Games Only records the game's own window, never the desktop: alt tab, chats and notifications stay out of the clip. `GameWatcher` scans the running processes every two seconds for a known game with a window on screen (not minimised), so a game started before LetsClip is found too, and counts it until its process exits, read from that one process's handle without listing processes again. It scans only while Games Only is on and nothing holds capture. Games Only can be turned on with no known game, the owner's pick: it then waits for one, Waiting for a Game or App on the chip. Since any app can be added, every word on screen says Games and Apps (the switch reads Games and Apps Only, the capture panel row Game or App, the dialog Games and Apps with Add Game or App); the setting keeps its `GamesOnly` name. Taking the recorded game off the list stops its recording at once (`GameWatcher.SetGames` lets go of it); before, it kept recording until the game exited. Known games are `GameScanner`'s Steam, Epic, Riot, Rockstar and Roblox libraries plus `Games` folders on C, D and E, with `UserSettings.AddedGames` added and `RemovedGames` taken out (`CaptureController.GameList`). Turning Games Only on or off stops the capture and starts the other source.
- Settings → Games and Apps Only → the Edit Games and Apps button (never a count, the owner's pick) opens `GamesDialog`: a search field (`MudHighlighter` marks matches) over one outlined table with no header and no cell borders, each row the exe's own icon, the name and a switch. The rows are every library game, every added app, every Start Menu shortcut to an installed exe (`GameScanner.ScanStartMenu` through `WScript.Shell`, Windows' own folder, uninstallers, LetsClip itself and browser web apps (`*_proxy.exe`: Netflix from the Store is an Edge web app whose window belongs to `msedge.exe`) left out, named by the shortcut; a launcher one folder below an app named only by its exe lends that app its name and goes, so G HUB is one Logitech G HUB row on `lghub.exe`, never also its `system_tray` launcher, `GameScanner.MergeLaunchers`) and every app open now (`GameWatcher.FindApps`). Switched on is recorded; switching a listed one off keeps its key in `RemovedGames`, switching an app on adds it to `AddedGames` with its exe path. Rows are ordered once when shown, switched on first, so a switch never moves its row. Icons come from `Icon.ExtractIcon` at 48 px, the one way every exe has (Steam's artwork exists only for Steam), clipped to the thumb radius; no description sits above the search. A Games and Apps button group left of the search (the owner's pick, the one button group in the app: an inset track, the picked half tonal blue, both `px-4` so the group never changes width) shows either the library games (`GameEntry.IsInstalledGame`, what `GameScanner.Scan` found) or everything else, Games first. Browse for an Exe adds anything else and switches to the half it lands in; the All chip on the left of the actions (a Select All button until 12 November 2026, see `Docs/Layout.md`) switches on every row shown (the half and the search), or all off once they all are, in one settings write (CaptureController.SetRecorded, which every switch now uses, where each row used to write alone); every app is keyed by `GameScanner.NormalizeProcessKey` of its process.
- Every ask (a setting, the page, the tray, Windows events, the game watcher, a dropped capture) runs `CaptureController.StepAsync` alone under one semaphore: it applies its change, works out the wanted `CaptureOptions` (null while held or with no game) and restarts only when that differs from the running session's `ReplayRecorder.Options`. Nine quick clicks on the capture panel restarted once, with the last values; 40 setting changes from several threads at once ended on one FFmpeg pair and one cache folder with the last values. Settings are written inside the controller's lock, so quick changes land on disk in order.
- A stop for a restart, a hold or exit first lets a running save finish (`WaitForSavesAsync`, 5 s at most), so a clip saved just before a change keeps its whole length. A press while capture starts or restarts is never refused: `CaptureController.SaveAsync` waits for the step (15 s at most) and saves what the new session holds, even a second of it, the owner's pick. Only Games Only with no game, a hold or an error says `Nothing is being recorded right now`. A press in Games Only with no game found reads the app in front at the press (`GameWatcher.ForegroundApp`, Windows' own hosts and LetsClip left out, named like the dialog names an open app) and the balloon says `Nothing is being recorded, click to record Overwatch from now on`; a click adds it like the Games and Apps dialog (`CaptureController.SetRecorded`, which also switches a removed one back on) and a quiet balloon confirms it, so a game no library scan knows (Battle.net, EA, Ubisoft, GOG, Xbox's `C:\XboxGames`) costs one missed clip instead of every clip. Each balloon carries its own click (`MainWindow.ShowBalloon`): before, any balloon, a Save Hotkey Taken or Clip Not Saved one too, opened the last saved clip.
- Starts and restarts stay out of sight: the chip and the tray read Recording throughout (`CaptureController.IsRecording`, `StatusText`) and the Save button stays enabled, never Starting or Stopping.
- First start defaults (`UserSettings`), the owner's pick: Games Only on, 30 s, 1080p (1440p costs a little more CPU and disk, see the Overwatch Field Test), 60 FPS, Normal, system audio on, the microphone on with Noise Cancellation on (on for everyone since 9 November 2026, the owner's pick, it was off), Start with Windows and Save Sound on, F10 (it takes F10 from every other app while LetsClip runs, Visual Studio's Step Over too, the owner's pick over Ctrl+Shift+F8), Automatic for both audio devices, Only Record Game and Discord off (the owner asked for it as something to turn on).
- Defaults the owner picks later reach existing users once: `UserSettings.DefaultsVersion` (a file without it reads as 0, so it predates them) below `CurrentDefaults` gets them and is saved at once, each version's block only for files below it. Version 1 set F10 and Automatic for both devices, version 2 turned the microphone on (checked: a version 1 file with the microphone off and F9 came back on version 2 with the microphone on and F9 kept). Raise `CurrentDefaults` and add a block for the next such pick, never reset what people chose without the owner asking.
- A PC with no microphone at all keeps the switch on and says so cleanly, the owner's pick: Automatic with no device of its kind (`E_NOTFOUND` from the default endpoint) records silence with no Problem, so no warning ever shows, and a microphone plugged in later becomes the default and connects through `DefaultDeviceChanged`. Settings' device field then reads `No Microphone Detected` (`No Output Device Detected` for system audio), greyed and disabled, and Test Microphone is disabled (`DeviceSelect.Missing`); the device lists stay null until Windows answers, so it never flashes while loading. Seen with the list emptied in a test build; a real PC without a microphone was not tried. A Bluetooth headset's microphone puts the headset in its hands free profile while open, so its sound drops to call quality for as long as LetsClip records with it; Automatic still takes it, the owner's pick on 9 November 2026.
- The reason a session ended names the exit code.

## Capture

- Monitors: `ddagrab` (Desktop Duplication) on the adapter and output that `MonitorCatalog` finds for the saved monitor's device path, never a stored index. The frame comes back unrotated: rotation 90 is `transpose=clock`, 270 `transpose=cclock`, 180 both flips (checked on the portrait LS27AG500N at 270).
- Game windows: `gfxcapture` (Windows Graphics Capture) on the window handle `GameWatcher.GameWindow` reads fresh at each start, with no yellow border, sized to the window's own shape inside the resolution box of the monitor holding it (`MonitorCatalog.ClientSizeOf`, `ReplayRecorder.FitInside`, never upscaled), so a maximised or windowed app gets no bars; only a window resized mid session is letterboxed (`resize_mode=scale_aspect`). The bars a v1.2 clip showed were that padding, never the desktop around the window. It sends a frame only when the window changes, so keyframes are forced each second of time (`-force_key_frames`), and the video stall check and slow frame rate warning are off for it: a minimised game sends nothing and only its exit ends the session, while a hung encoder is caught by a probe (see Recovery). A window still from its first moment sends one frame, which AMF and x264 both hold (`-latency 1 -async_depth 1` did not release it on AMF, only x264's `zerolatency` did), so no segment ever closes; up to v1.7 such a start failed every encoder after 12 s and retried with an error, which a paused YouTube window hit on 6 November 2026. A window session now counts as started once its audio writes a segment, or at the 12 s timeout while FFmpeg still runs (`CaptureSession.LaunchAsync`), since `VideoEncoders.WorksAsync` already proved the encoder; video flows the moment the window draws, and a save before that says `Nothing has moved in the window yet`. An `overlay` onto a paced `color` source does not help: frame sync waits for the window's next frame too.
- Resolution is a select of `UserSettings.ResolutionChoices` (480p, 720p, 1080p, 1440p, 2160p) below the picked monitor's short side plus the monitor's own size, labelled by that side (`CaptureController.ResolutionChoices`). A choice fits its 16 by 9 box in the monitor's orientation, never up (`ReplayRecorder.OutputSize`, 480p is 854 x 480); one at or above the short side is the monitor's own size. The saved value is the picked lines (`UserSettings.Resolution`, 1080 by default), and a monitor without it takes the nearest below, like frame rates. Frame rates are `UserSettings.FrameRateChoices` up to the monitor's refresh rate, which `MonitorCatalog.DisplayDetails` takes from the `QueryDisplayConfig` path's own fraction rounded with `Math.Round` (59.94 Hz reads 60, 143.86 Hz 144, never 59 or a decimal), the owner's pick; every shown rate, log and choice uses that one number. `DEVMODE`'s `dmDisplayFrequency` truncates, so it read 59 on a 59.94 Hz screen.
- `hwdownload`, then one CPU `scale` with Lanczos and BT.709 limited range, then `nv12`. Lanczos costs nothing over bilinear and scores 10 VMAF higher (see the Overwatch Field Test). On the CPU route a window up to 2560 x 1440 is read back at its own size and this `scale` sizes it (`CaptureSession.MaximumWholeWindowPixels`); above that, and on Quick Sync, `gfxcapture` still sizes it on the GPU, since a 4K readback costs a core. Measured with the window shown: 2560 x 1440 to 1080p at 60 FPS takes about half of one CPU core for the video process, 2560 x 1440 native at 240 FPS about two cores and 606 MB, holding 240 FPS (7198 frames in a 30 s clip).
- Intel Quick Sync converts on the GPU instead (`VideoEncoders.QuickSyncGpu`, `GpuFrames`): `hwmap=derive_device=qsv`, then `vpp_qsv` sizes, turns (`transpose` clock, cclock, reversal) and makes `nv12` with BT.709 limited range. Measured in November 2026 on an i5-1335U with Iris Xe and FFmpeg 9.0.2: Desktop Duplication at 1080p60 takes 21% of a core against 83% on the CPU route, window capture 4.8 against 13.9 ms of CPU per frame, both holding the rate (10,798 frames in 3 minutes with a build running); colour bars score 43.9 dB for the conversion alone (CPU `scale` 42.6) and 48.6 after encoding (45.1), limited range on both. Downscaling 1440p to 1080p is softer (40 to 42 dB against Lanczos in every `scale_mode`, CPU bilinear 44.3), so only a monitor above 1080p recorded at 1080p differs. A failed GPU start falls back to the CPU route on the same encoder without a warning. `scale_d3d11` fails on Iris Xe too (`E_INVALIDARG`); AMD and NVIDIA keep the CPU route, NVENC untested.
- AMD and NVIDIA keep the CPU route, the owner's pick after a full GPU research on 6 November 2026 (RX 9070 XT, FFmpeg 9.0.2, a YouTube video playing): it is simple, the same for every GPU vendor and both capture modes, and already as light as the popular tools. A published 1080p60 test on a Ryzen 7 7700X put ShadowPlay at 2.4% of the whole CPU, Xbox Game Bar 3.7% and Medal 5.1%; LetsClip's 1080p60 monitor capture is 40 to 55% of one core, 5 to 7% of the owner's 7800X3D (which reports 8 threads), and window capture, the default, about 19% of one core. Those tools keep frames on the GPU and convert colour there (OBS hands NV12 textures to its GPU encoders); LetsClip downloads each frame and converts it with `scale`, which costs most at high frame rates, never at 1080p60. What the research found, all with `-frames:v 120` runs so no AMF process was killed:
  - AMF encodes D3D11 NV12 textures (a `hwupload` of NV12 into `h264_amf` worked) but refuses D3D11 BGRA (init fails with -22 for uploaded BGRA, `SubmitInput` fails for `ddagrab` frames), so a GPU route needs a BGRA to NV12 step on the GPU.
  - `scale_d3d11` (options `width`, `height`, `format`, only `nv12` or `p010`) cannot create its output pool on AMD: `Could not create the texture (80070057)` even for uploaded test frames. Its pool asks for `D3D11_BIND_RENDER_TARGET | D3D11_BIND_VIDEO_ENCODER` in a texture array of 10, and AMD's D3D11 driver has no D3D11 video encoder, so the bind flag is the likely cause. It fails the same way on Iris Xe. When a newer FFmpeg drops that flag, `hwdownload`, `format=bgra` and `scale` become `scale_d3d11=width=W:height=H:format=nv12` straight into the encoder for every vendor and both modes: recheck on every FFmpeg update.
  - `vpp_amf` refuses D3D11 input (`AMFConverter-Init() failed with error 10`, not supported) from `ddagrab` and from an upload alike, but converts AMF surfaces fine (`vsrc_amf`, or BGRA uploaded to an `amf` device).
  - `hwmap=derive_device` from `d3d11va` to `vulkan` or `d3d12va` is not implemented (-40), to `amf` fails (-22), so `scale_vulkan`, libplacebo, `h264_vulkan` and `h264_d3d12va` cannot take capture frames. `h264_mf` on `ddagrab` frames fails with a generic external error.
  - The one working GPU-only route is AMD's own capture: `-init_hw_device amf=a -filter_hw_device a`, `vsrc_amf=monitor_index=0:framerate=R`, `vpp_amf=w=W:h=H:format=nv12:color_profile=bt709:out_color_range=studio`, `h264_amf` (it cannot take `vsrc_amf`'s BGRA itself: `encoder->Init() failed with error 10`). Over 30 s its FFmpeg used 8% of a core at 1080p30 against 30%, 20% against 41% at 1080p60, 21% against 69% at 1440p60, 19% against 29% at 720p60, 36% against 98% at 1080p120 and 46% against 132% at 1080p144, the video engine as busy as before. It is not used: it captures monitors only, never a window, so the default mode gains nothing; it is AMD only, so a second pipeline next to the one every vendor needs; its framerate tops out at 200 (`Failed to set framerate: 5` from 210 up), so 240 still needs the CPU route; it opens every session with 0.63 to 0.79 s of nothing, its stamps jitter (60 repeated at 1440p60) and it ran 9 to 11 frames short in 30 s at 120 and 144 FPS (one 10 s run gave 40 FPS at 60); and its own capture thread polls, `capture_mode=wait_for_present` sends only on presents (16 FPS), `get_current` spins a core at 278 FPS. It turns a portrait monitor upright by itself (1440 x 2560) and has no cursor option; whether it draws the cursor was never seen.
  - Downloaded BGRA fed to AMF halves the CPU at 240 FPS (0.84 cores against 1.70), but AMF's own conversion scored 36.6 dB on colour bars against 44.6 dB for the `scale` above, and its range follows the input's tags (full range from `ddagrab`), so it is not used. `fast_bilinear` saves no CPU per frame and drops to 39.6 dB. Converting to `nv12` before scaling, or `scale` with `threads=4`, saved nothing at 144 or 240 FPS: what limits 240 FPS on a 2560 x 1440 monitor is reading the frames back from the GPU, about 3.5 GB/s. Colour checks use known bars, never the live screen, whose frames already differ at 24 dB.
- The first Quick Sync use from a freshly written FFmpeg copy is slow on the i5: the first encoder test after the v1.7 build and the v2.0.1 update took 7.6 and 9.3 s, a harness's new FFmpeg copy 6.3 s, and every later one 0.55 to 0.75 s, the GPU idle for 5 minutes or not. It is not the exe's path alone (a copied folder took 1.1 s), not the GPU's idle state and not the D3D shader cache (nothing written during it); the cause was not found and no public report matches. So in Games Only, where the start waits for a game, `CaptureController.StartAutomaticallyAsync` runs the first encoder's test in the background at launch for the picked monitor's box and frame rate (`WarmUpEncoderAsync`): the slow first test after an update lands where nobody waits, and its pass is cached, so a fullscreen game on that monitor skips the test entirely. A start during it runs its own test beside it; sharing one was left out, since an export's test carries its cancel.
- The encoder is the first that really encodes a few test frames (`VideoEncoders.WorksAsync`): AMF, NVENC or Quick Sync for each GPU vendor present, then x264. A one second GOP, no B frames, and `h264_metadata` writes the BT.709 colour description the hardware encoders leave out. Rates grow with the pixel rate: load is the square root of pixels per second over 1080p60, at least the frame's own share of 1080p (1 from 1080p up, 0.67 at 720p, 0.44 at 480p), the average 20 Mbps and the peak 40 Mbps times the load. Only AMF and x264 are tested on this PC. x264 captures with four threads (`-threads 4`): by default it starts about one and a half per core, each holding frames, so a 1080p60 monitor capture held 643 MB and dropped to 56 FPS on the i5's 12 threads; four threads hold 318 MB and 60.4 FPS through the app's own session, two 270 MB, and a noisy 1080p60 pattern scores the same either way (38.33 dB, 13.2 MB). Thread caps change nothing on the GPU routes (Quick Sync 217 to 247 MB whatever `-filter_threads` or `-async_depth`), so only x264 gets one.
- Quality is Normal, High or Max (`CaptureQuality`, Normal by default): High gives 1.75 and Max 2.5 times the average and peak bits, with quality level 22, 19 or 16 for NVENC's CQ, Quick Sync and x264's CRF, and 42, 48 or 51 for AMF's QVBR, which counts up (`VideoEncoders.TuningOf`); the replay cache grows with the peak. Up to v1.2.1 AMF got 22, 19 and 16 too, so Max recorded worse than Normal on AMD: a 1440p clip of a film came out at 1.18 Mbps. The AMF levels are matched to x264 by PSNR on a noisy 1440p60 pattern (AMF 42 32.13 dB at 33 Mbps against CRF 22 32.11 dB at 28 Mbps, AMF 48 32.23 dB against CRF 19 32.25 dB). Rechecked on 6 November 2026: on real footage (a 1440p YouTube clip scaled to 1080p) levels 44, 46, 48, 50 and 51 gave 36.5, 39.7, 41.7, 43.2 and 46.9 Mbps, so High spends about 27% and Max 43% more than Normal; on pure random noise High and Max came out byte for byte the same (59.1 Mbps), and with heavy noise AMF's QVBR ignored `-maxrate` (327 Mbps against 40M), which only `SegmentCache`'s byte bound then limits. PSNR against a decoded, already lossy clip stayed near 26 dB for every level, so quality is compared on clean synthetic sources only.
- One second MPEG-TS segments from the `segment` muxer, each listed on standard output as `name,start,end`, with `mpegts_copyts=1` so the files keep the media clock. `SegmentCache` keeps the replay length plus three seconds, within 1.5 GB or the replay length at the peak rate plus 20%, whichever is larger, and never evicts past a pinned save.
- Noise Cancellation (`UserSettings.NoiseCancellation`, on by default, always shown under Microphone and disabled while the microphone is off) cleans only the microphone: `AudioMixer` then writes four channels, system audio on the first two and the microphone on the last two, and the audio FFmpeg runs `CaptureSession.MicrophoneCleaning` (`highpass` at 80 Hz, `afftdn` at 20 dB with noise tracking from a -45 dB floor, then `agate` at -40 dB, ratio 3, 24 dB down, 5 ms attack and 250 ms release) on those before `amix` puts them back to stereo. The owner still heard the room with v1.8.4's chain (12 dB, a -50 dB gate): measured on a synthetic voice at -30 dB RMS over pink noise, it took a -47 dB room only to -53 dB, since that gate opened on the room itself. The current chain takes the same room to -78 dB and a -41 dB room to -51 dB, while a -30 dB voice and a quiet -38 dB one keep their level within 0.6 dB and a word's first 50 ms reads as before. There is no strength setting, the owner's pick: one gentle sensitivity for everyone. Measure any change the same way (`aevalsrc` harmonics gated on and off, `anoisesrc` pink at 0.03 and 0.06, `astats` RMS of a gap, a word and its onset) before shipping it.
- Only Record Game and Discord (`UserSettings.OnlyGameAndDiscord`, off by default), the owner's request on 9 November 2026 after Games and Apps Only still recorded every sound Windows played: in the Audio panel under System Audio, greyed while Games and Apps Only or System Audio is off (like Noise Cancellation under the microphone), and while it applies the output device select greys out too, since a process's own sound ignores the device. A game window's session then records no device loopback: `CaptureController.WantedOptions` puts the found game's process (`GameWatcher.GameProcessId`) in `CaptureOptions.GameProcess`, and `AudioMixer` opens a process loopback (`WasapiRecorderBuilder.WithProcessLoopback`, `IncludeTargetProcessTree`, `BuildAsync` waited for on the pool thread) for the game and one for each running Discord build (Discord, PTB, Canary, Development, `GameWatcher.DiscordProcesses`: the oldest process of each name started the rest, so its tree holds every voice). Every 10 s `AudioMixer.FollowDiscord` adds a build that started and drops one that closed, without restarting the session; its sources are a whole array swapped under `_sourcesGate`, so the writer reads one list per chunk. Monitor sessions, and Windows before 10 2004 (`AudioMixer.CanRecordProcesses`, build 19041, which NAudio requires; Microsoft's docs say 20348), keep the device loopback. These sources ignore `MuteSystemAudio`, since LetsClip's own chime, microphone test and editor preview never sound in a game's or Discord's tree, so in this mode none of them reach a clip and the game's sound is never cut for a chime. Measured on 9 November 2026 on the 7800X3D (build 26300) with a test window keyed as the game playing 440 Hz, a copied tone app named `DiscordCanary.exe` playing 660 Hz and an outsider playing 880 Hz, all at -26 dBFS, each band read with `bandpass` and `astats` from a saved clip: on, 440 and 660 at -29 dB and 880 at -56.6 dB (the filter's leak from the other tones, -63.9 dB with only one other playing); off, all three at -29 dB; a Discord build started 15 s into the session joined 8 s later, absent before and -29 dB after. Process loopback sends packets of zeros while its target is quiet and even for a process that does not exist, with QPC times about 10 ms behind, the same as a device loopback, so the media clock code is unchanged. It cost LetsClip 1.3 to 1.7% of a core against 0.5 to 0.7% with the device loopback (three trees followed, the real Discord among them) and 10 MB more. Not tried: a game behind anti-cheat, Windows 10, and builds around 26200, where one public report (MeetCap #38) had NAudio's process loopback deliver only zeros.
- Audio runs in a second FFmpeg process. In one process the scheduler held the live video back whenever the piped audio lagged the video by 100 ms, and capture fell to 6 FPS; apart, both run free.
- `FFmpeg.Start` opts every child out of power throttling (`SetProcessInformation`, execution speed and timer resolution). Windows throttles the children of an app whose window is shown, even when covered, and capture fell to 35 to 45 FPS whenever the LetsClip window was open; hidden to the tray it was always 60. A sibling FFmpeg started outside LetsClip never slowed, which is how it was found.
- Monitor frames are timed by their count, not by `ddagrab`'s stamp: `ddagrab` stamps each frame with the moment it was grabbed, rounded to the frame grid, so with the CPU busy (a game plus the encoder) a late grab took the next slot and the one after it doubled up, a frame held twice as long. A 30 s Overwatch clip at 1080p60 had 15 of them, a 30 s x264 test 115, and a 240 FPS clip read as jumping and pausing. `setpts` now puts frame N in slot N from the first frame and re-anchors only past 1.5 slots of real drift (`CaptureSession.VideoArguments`); the same load then gave 1803 frames all 16.7 ms apart. Capture alone, idle, was always exact. Window capture keeps its own stamps, since a window sends frames only when it changes, and `-fps_mode vfr` drops a second frame that rounds into a slot already taken: with `passthrough` a 60 FPS window clip of a 240 Hz window held 1873 frames, 73 of them stacked on a used slot, and a 144 FPS one 1108; with `vfr` the 60 FPS clip holds 1800, all 16.7 ms apart. Rounding alone still dropped 10 to 25% of the frames whenever a game drew at about the capture rate (a 60 FPS game at 60, 120 at 120), since presentation jitter put two neighbours in one slot and left the next empty: a test window drawing at about 115 Hz kept 3221 of 3600 frames at 120 FPS. A window frame whose slot is taken now takes the next one, at most one slot late, and only a frame two slots behind its predecessor drops (`ld(3)` holds the last slot, `CaptureSession.VideoArguments`, November 2026): the same window keeps 3432, every frame it delivered, and a simulation of 120 on 120 and 144 on 144 went from 909 and 630 drops in 30 s to none, a 59.9 or 60.1 FPS game at 60 from about 490 drops in two minutes to 0 and 11. A window frame then sits at most 1.5 slots after its real time. Slower windows keep their empty slots (a 144 FPS clip of a 100 Hz window holds some frames for two slots), as any sampling of them would.
- The media clock: `AudioMixer` places each WASAPI packet at its QPC time (sample zero is the session's start, media time 1.0), silence and gaps stay silence, and a packet within 20 ms of the last one continues it.
