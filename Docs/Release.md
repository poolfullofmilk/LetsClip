# LetsClip, Publish, Screenshots And Updates

Notes behind the build and publish commands, the screenshots every release takes, and how updates check and install. Read before a release or before touching `Updater`, `StartupRegistration` or the csproj. Part of `CLAUDE.md`, its rules bind the same way.

## Publish Notes

The publish folder holds only `LetsClip_v<Version>.exe`: `IncludeAllContentForSelfExtract` and the `BundleWebRoot` target pack `wwwroot` and the `FFmpeg` folder inside it, extracted once on first start. The exe is ReadyToRun (`PublishReadyToRun`), so the first page opens sooner. `LetsClip.Desktop` keeps the Windows SDK version in `net10.0-windows10.0.17763.0`: the app itself uses no WinRT, but `BlazorWebView`'s `WebView2CompositionControl` loads `Microsoft.Windows.SDK.NET` when the window loads. Plain `net10.0-windows` built and published 16.5 MB smaller and then failed there with a `FileNotFoundException`, the page never showing (tried in the November 2026 audit). A build without the FFmpeg files stops with a message (`RequireFFmpeg`, before `BeforeBuild`: hooked to `Build` it ran after the copy step, which failed first on the missing `LICENSE.txt`).

The page host stays .NET 10's `BlazorWebView`, which hard codes `WebView2CompositionControl` and copies every WebView2 frame into WPF, the owner's pick on 9 November 2026: wait for .NET 11's switch to the classic HWND control (asked for in dotnet/maui #39658 and #40003) rather than pin an older package. Measured that day on the 7800X3D in a Debug sandbox, a 30 s 1080p60 clip playing in the editor: LetsClip itself 12.5 to 15.8% of a core with 10.0.120 against 0.6 to 1.0% with 9.0.120 (the HWND host), WebView2 12 to 17% either way, 660 against 540 MB private, the same dropped frames (4 to 6 of 1440); idle Clips pages cost the same, 431 against 347 MB; the hover preview cost LetsClip 9.6% with the composition host. 9.0.120 worked against Blazor 10 (it pulls `Components.WebView` 9.0.9 under `Components` 10.0.1), Settings, the Games and Apps dialog and the editor rendered with no console errors, and plain `net10.0-windows` then built and played (23 MB smaller output, no Windows SDK projection). Not chosen: an unsupported package mix, and full screen and resizing were never checked on it. When .NET 11 lands, switch to the HWND host, try plain `net10.0-windows` again and measure the same way.

`.github/workflows/build.yml` fetches the pinned FFmpeg and builds in Release on `windows-latest` for every push and pull request. Releases are made by hand, the shared way: the exe as the only asset and an empty body, and only once the owner has tried the build left running for them and said publish. A patch number is the owner's pick when asked for (1.8.2, released on 6 November 2026); `AppInfo.VersionText` then shows three parts. Never publish a version that is already out under the same tag: every installed copy of it would never see the new build, since `Updater` only offers a higher version. On 9 November 2026 the owner asked to publish v2.0.2 while v2.0.2 was already the latest release, and picked v2.0.3 when asked. Every shown version reads like its tag, `v1.8.2` (`AppInfo.VersionText` carries the `v`): the update snackbar, About and the update dialog. From PowerShell, `gh release create` takes the empty body as `--notes-file` of an empty file: PowerShell drops an empty `--notes ""` argument, which shifted the exe into the tag position. After a release check that `releases/latest` redirects to the new tag and that the asset's `digest` matches the local exe, since `Updater` refuses an update without it.

The owner's install lives in `%LocalAppData%\Programs\LetsClip` (v1.8 placed there on 6 November 2026). A build left running for the owner goes there through an `explorer.exe`-started `.cmd`, so it runs outside the app container on the real profile and its first Release start rewrites the Run value and the Start Menu shortcut to that path; a test exe started anywhere else leaves the Run value pointing at it, which happened with a v1.7.1 test build that was later deleted. Killing the owner's copy mid recording can hang AMF for the next start, as it did on 8 November 2026 (the install script started the new exe 3 s later, its 1080p60 session timed out at 12 s and fell to x264), so the script waits 10 s before starting it.

A Release exe someone started from `bin\Release` locks that folder; publish to another folder with `-p:BaseOutputPath=<folder>\` rather than stopping it. A `BaseOutputPath` outside the project lets the project's own `bin` folder into the publish folder as content (`bin\Debug\...\*.json` showed up beside the exe), so the release asset itself is published to the default `bin\Release` once nothing runs from there.

## Updates

`Updater.CheckAsync` reads the `releases/latest` redirect without following it, so it needs no token. No setting, the owner's pick on 9 November 2026: until then it ran only when the page was first built, so a copy started in the tray at sign in and never opened never learned of an update. Now `MainWindow.KeepUpdatedAsync` checks at launch, page or not, and every 6 hours (`s_updateCheckPeriod`), every time the window is shown checks too (`RestPageAsync` calls `FindUpdateAsync`), and **More (⋮) → Check for Updates** still asks by hand. A newer release goes to `DesktopShell.ReportUpdate`, which keeps the newest one (`AvailableUpdate`, outliving any page) and raises `UpdateFound`: `UpdateDialog`, titled `LetsClip v2.0.1 is Out`, opens once per release per run (`TakeUnofferedUpdate`, on that event and on the page's first render, so a release found in the tray is offered when the window opens and never again after the X), and the red dot stays until restart: a `MudBadge` on the More menu (`d-flex`, or it lifted the button 2 px), then `update-dot` on Check for Updates. A check by hand always opens the dialog (`ReportUpdate(offered: true)`). The dialog shows no release notes, since every release body is empty; `AppInfo.ReleaseApiUrl` only feeds the checksum lookup below.

Updates also install themselves, the owner's pick: "it doesn't matter it was recording, just update in the background". `MainWindow.InstallWhenIdleAsync` waits, checking each minute, until the window has been hidden for 10 minutes (`_hiddenSince`, from launch for a tray start; the same 10 minutes after which the page is released) with no export running and no save under way, then logs `Began Installing Update`, downloads, starts the new exe in the tray and exits; the new version records again by itself, so only the unsaved replay is lost. A failure logs its type and waits for the next 6 hour check. Debug, sandboxed and renamed builds only log `Found Update vX, Only A Release Exe Installs It Itself` (`Updater.CanInstall`). Checked on 9 November 2026 with a sandboxed Debug build stamped `-p:Version=0.9`: a tray start logged the release within a second without building a page, opening the window showed the dialog and the red dot, closing it and opening the window again showed no dialog with the dot kept, and Check for Updates showed it again. The background download, launch and exit were not run end to end, since only a Release exe outside a sandbox may install (it would rewrite the owner's Run value); they share their code with Update Now.

Update Now hides the X and Escape until the download fails (`UpdateDialog.SetClosableAsync`) and calls the same `MainWindow.InstallUpdateAsync` as the background, which allows one install at a time (`_isUpdating`; a dialog pressed during a background download just waits for it). `Updater.DownloadAsync` saves the new exe beside the running one through a `.download` file that must match the asset's SHA-256 `digest`; a mismatch or missing digest opens the release page instead. `Updater.Launch` starts it with `--after-update <pid> <path>`, plus `--tray` while the window is hidden, and the window exits through `MainWindow.ExitAsync`, finishing saves. The new exe runs `Updater.WaitForPreviousVersion` before the single-instance check, up to 60 s for the old process (which may finish a save for up to 15 s first), and only at the end of a successful start `DeletePreviousVersion` removes that one exe, never every `LetsClip_v*.exe` beside it, so a version that cannot start leaves the last one in place. New versions pass their own path, an older one is asked for it while it runs. A protected folder, a Debug build or a renamed exe (`Updater.CanInstall`) opens the release page. Build with `-p:Version=0.9` to see the dialog.

## Install Folder And Update Safety, 10 November 2026

- The exe lives in `%LocalAppData%\Programs\LetsClip` (`AppInfo.InstallDirectory`). A Release start outside a sandbox from anywhere else copies itself there when no copy of the same name and size exists, starts it with the same arguments and exits (`Updater.MoveToInstallFolder`, first thing in `App.OnStartup`); a folder that cannot be written means it runs where it is. Updates download into that folder. The file in Downloads is the person's own and stays. Seen on the owner's PC before this: the Run value and the shortcut pointed at `Downloads` while a second copy sat in the install folder.
- The shortcut goes straight into `Start Menu\Programs`, or into `Programs\01 Apps` where that folder already exists, so the owner's machines stay as they are and nobody else gets a folder named 01 Apps. The owner has not confirmed this, it was the handoff's neutral option. A failed registration is logged.
- `UserSettings.AttemptedUpdate` holds the tag of an update that was launched. `Tray.InstallUpdateAsync` writes it before starting the new exe, `Tray.InstallWhenIdleAsync` skips a release with that tag (Update Now by hand still installs it), and a version at or above it clears it at the end of a good start. A failed download writes nothing, so the next check tries again.
- A new version that throws in `Start` after `--after-update` hands back to the exe it replaced when that is another file (`App.OnStartup`). A version before this one that is handed back to has no `AttemptedUpdate`, so it would install the broken release again; nothing can fix a version already out.
- `Tray.KeepUpdatedAsync` catches whatever a check throws, so one failure never ends the checks.
- Tested outside a sandbox on 10 November 2026 with a scratch copy carrying test only hooks (a local file as the update, 15 s as idle, an install folder beside the repository), an old v0.0.1 and a new v9.9.9, the owner's Run value, shortcut and settings saved first and put back after: started from a download folder it ran from the install folder 12 s later with the Run value on it; an update throwing in `Start` left v0.0.1 running, the broken exe deleted, the Run value back on v0.0.1 and `Skipped Update v9.9.9, It Did Not Start Before` in the log, still so 30 s later; an update exiting silently left nothing running and the old version, started again, skipped it; a good update ended on v9.9.9 with the old exe deleted and `AttemptedUpdate` null. A copy without the update hook then found the real v2.0.3, downloaded it in 3.3 s, started it and was deleted by it: the first time the background install ran end to end.
- Signed updates (the handoff's finding 11) are not built, they add a release step and a key the owner must keep: ask first. A stable exe name is not built either.

## .NET 11 And The Plain WebView2 Host, 11 November 2026

- All three projects target .NET 11 (`net11.0`, `net11.0-windows`, and `net11.0-windows` for the app too), `Microsoft.AspNetCore.Components.WebView.Wpf` is 11.0.0, the workflow builds with `11.0.x`. `MainWindow.EnsurePage` sets `UseCompositionControl = false`, so the page lives in the plain `WebView2` (an HWND) and WPF no longer copies every frame. This is the switch the notes above waited for; the property exists only in the .NET 11 package and must be set in the initialiser.
- Measured on the 7800X3D, published exe, a 30 s 1080p60 16 Mbps clip playing in the editor, three rounds of 20 s each: LetsClip 5.5 to 10.2% of a core and 244 to 275 MB private on .NET 10, 0.2 to 2.7% and 112 to 151 MB on .NET 11; WebView2 the same either way (5 to 14%), dropped frames the same (0 to 4 of about 1,330).
- The app project no longer needs the Windows SDK version in its target: plain `net11.0-windows` builds, publishes and starts alone from an empty folder with its page. The exe is 168.2 MB, against 178.7 MB on .NET 10 and 185.7 MB on .NET 11 with the SDK projection.
- Checked on the plain host with the lone exe: the page and its cards, the hover preview (playing), the monitor overlays (a second window while the monitor list is open, gone after), resizing from outside (the page follows), full screen in and out by Escape and by double click, a renderer crash (`Page.crash`, the page reloads on the same clip) and a browser crash (`Browser.crash`, cards back in 1.5 s). Nothing in WPF is ever drawn over the page, so the airspace limit of an HWND host does not apply.
- Full screen left the window screen sized when it came back (2560 x 1380 instead of 1600 x 1025); `MainWindow.ShowFullScreen` now keeps the window's own size and puts it back. Whether the composition host did the same was not established.
- Full screen needs a focused window and a real gesture: a script's `requestFullscreen` answers `not granted` while the window has no focus, and CDP mouse events did not count. The test moved the real pointer and double clicked. A leftover Windows Script Host error dialog once sat over the window and ate those clicks: look at the screen before believing such a test.
- `_page.WebView` is an `IWebView2` in .NET 11, so hiding it for the tray casts to `UIElement`.
- .NET 11's analyzers asked for three things, all done: every `InvokeVoidAsync` guarded (one `PageScript.CallAsync` extension that swallows `JSDisconnectedException`, used by every component, which removed four hand written try blocks), no `StateHasChanged` in handlers that render anyway (`OnKeysDone` renders for its script caller instead), and no `Task.Delay` left running after a `Task.WhenAny` (five places cancel theirs, `UpgradeAsync`'s 30 minute timer among them). `ExportPanel.Request` went, its one use builds the request.
- The publish notice `NETSDK1244` about `IncludeAllContentForSelfExtract` is turned into a message in the Release group: the app needs FFmpeg and `wwwroot` on disk, so the extraction stays.
- The SDK: see the working agreement in `CLAUDE.md`, it sits in a user folder until installed machine wide.

## Signed Updates, 11 November 2026

- The owner asked for it on 11 November 2026 (the handoff's finding 11): since installs are silent, whoever can publish a release on the GitHub account could run code on every PC. GitHub's asset digest only proves the download.
- Each release's exe is signed with ECDSA P-256 over SHA-256 by a key that never leaves the owner's PC (`C:\Users\yusuf\.letsclip\update-signing.pem`, PKCS 8, made with OpenSSL). The signature, base64 of OpenSSL's DER form, is the release body, its only content, so the exe stays the only asset. The public key is `Updater.SigningKey`.
- `Updater.DownloadAsync` reads the body with the digest (`ExpectedDetailsAsync`) and, after the digest matches, verifies the downloaded file (`IsSigned`). No body, a malformed one or a wrong one throws `InvalidDataException`: Update Now then says `The download could not be verified` and opens the release page, the background install logs and leaves the running version recording.
- `Updater.SelfTestPasses` (Debug, in the static constructor) checks a known signature, a changed byte, a missing and a malformed signature. Checked outside it too: the published exe signed with OpenSSL verified through `IsSigned`, another exe with that signature did not.
- v2.0.3 and older check no signature, so they update to v2.0.4 as before. From v2.0.4 on a release without a valid body is never installed by itself.
- Signing a release, in Git Bash: `openssl dgst -sha256 -sign ~/.letsclip/update-signing.pem LetsClip_v<version>.exe | base64 -w0 > signature.txt`, then `gh release create ... --notes-file signature.txt`. To check a published release: `gh release view v<version> --json body -q .body` must equal the file, and a throwaway that calls `Updater.IsSigned` on the downloaded asset must say true.
- First signed update end to end, 11 November 2026, on the owner's install: v2.0.4, started in the tray, logged `Began Installing Update v2.0.5 In The Background, Hidden For 10 Minutes`, downloaded it in 6.0 s (digest and signature checked), started it and exited; v2.0.5 was up 8.3 s after the install began, cleared `AttemptedUpdate`, deleted the old exe, and the Run value and shortcut point at it.
- A check logs nothing, found or not. The first try that day found no update and gave no reason: v2.0.4 had been restarted 12 s after the previous release was deleted, and its one check at launch came back empty (the same request answered v2.0.5 minutes later), so nothing happened until a second restart. Delete the previous release only after the installs have updated, or wait a minute before restarting one. Worth a log line for every check.
- Losing the key: no new release can be signed, installs stay on their version and say the download could not be verified when asked by hand. The way out is a release with a new public key that people download themselves. Keep a copy of the key off this PC.
