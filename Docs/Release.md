# LetsClip, Publish, Install And Updates

The build and publish notes, the screenshots every release takes, how LetsClip installs, updates and uninstalls itself. Read before a release or before touching `Updater`, `StartupRegistration` or the csproj. Part of `CLAUDE.md`, its rules bind the same way.

## Publish

- One self contained exe, `LetsClip_v<Version>.exe`: `IncludeAllContentForSelfExtract` and the `BundleWebRoot` target pack `wwwroot` and the `FFmpeg` folder inside it, unpacked once on first start; ReadyToRun, so the first page opens sooner. `NETSDK1244` about the extraction is turned into a message in the Release group, since the app needs FFmpeg and `wwwroot` on disk. A build without the FFmpeg files stops with a message (`RequireFFmpeg`, before `BeforeBuild`).
- All three projects target .NET 11, the app plain `net11.0-windows`. The page lives in the plain HWND `WebView2` (`UseCompositionControl = false`, set in `MainWindow`'s initialiser, a .NET 11 package property): playing a 1080p60 clip in the editor cost LetsClip 0.2 to 2.7% of a core and 112 to 151 MB, against 5.5 to 10.2% and 244 to 275 MB with .NET 10's composition host (11 November 2026). Nothing in WPF is drawn over the page, so the HWND airspace limit never applies.
- The exe is 105 MB since LetsClip's own slim FFmpeg (14 November 2026), 168 MB with the BtbN build, and unpacks to about 233 MB in `%Temp%\.net\LetsClip\<id>`, 432 MB before.
- The csproj stamps the commit a build came from (`AddCommit`, the SDK's `SourceRevisionId` into an `AssemblyMetadata` named Commit, `AppInfo.Commit`), which What Changed reads. So a release is published again after its commit, never before it, or every install would list one release too many.
- A Release exe started from `bin\Release` locks that folder; publish to another with `-p:BaseOutputPath=<folder>\`. A `BaseOutputPath` outside the project lets the project's own `bin` into the publish folder as content, so the release asset itself is published to the default `bin\Release` once nothing runs from there.
- `.github/workflows/build.yml` fetches the pinned FFmpeg, builds in Release with warnings as errors, runs `dotnet format analyzers` and `style` at info on every project and `csharpier check .` (CSharpier 1.3.0, the owner's version) on every push and pull request. RazorStyle and the comment length check stay local.

## Releasing

- Releases are made by hand, the shared way, once the owner said publish. The release body is the exe's signature and nothing else, the exe the only asset (Signed Updates below). Never publish a version already out under the same tag: installs only take a higher version. Every shown version reads like its tag, `v2.0.10` (`AppInfo.VersionText`).
- From PowerShell, `gh release create` takes the body as `--notes-file`: PowerShell drops an empty `--notes ""` argument, which once shifted the exe into the tag position.
- After a release: `releases/latest` must redirect to the new tag, the asset's `digest` must match the local exe and the body must verify. Delete the previous release only once the owner's install updated, or wait a minute before restarting one: a check right after the delete once came back empty.
- The FFmpeg build is a pre-release of its own, `ffmpeg-9.0.2-letsclip-1`, with `ffmpeg-9.0.2-letsclip-1.zip` as its asset. `releases/latest` never lists a pre-release, so no install sees it. It is never deleted with an app release: `Get-FFmpeg.ps1` downloads it, for every build and for CI.

## Install, Update, Uninstall

LetsClip installs itself, keeps one exe under one name, and leaves an entry in Settings, Apps to remove it.

- The installed exe is `%LocalAppData%\Programs\LetsClip\LetsClip.exe` for every version (`AppInfo.InstallPath`), the owner's pick of 14 November 2026. Windows keys the tray icon's place, a GPU preference and Controlled Folder Access by path, so before this every update dropped the icon back into the overflow (the owner's PC listed one unpinned entry per version).
- `Updater.MoveToInstallFolder`, early in `App.OnStartup` after `WaitForPreviousVersion`: a Release exe outside a sandbox that is not the installed exe copies itself to `LetsClip.exe`, starts that copy with its own arguments plus `--installed-from <itself>` and exits. The copy deletes the download once it exits (ten tries a second apart, only a `LetsClip_v` exe, never the running one). A folder that cannot be written means it runs where it is.
- A newer download while an older install runs takes over (`Updater.TakeOver`): the running `LetsClip.exe` is renamed aside to `LetsClip_v<its version>.exe` (Windows lets a running exe be renamed), the new one copied in, the old one asked to exit through the `LetsClip.Exit` event (`AppInfo.SignalName`, a sandbox gets its own), and the new one started with `--after-update <old pid> <aside>`. The same or a newer install only shows its window, through the single instance.
- An update downloads `LetsClip_<tag>.exe` into the install folder (`Updater.DownloadAsync`), then `Updater.Launch` renames the running `LetsClip.exe` aside to `LetsClip_<its tag>.exe`, gives the download the installed name and starts it with `--after-update`. A rename refused leaves the download as it is, which then takes the name itself through `MoveToInstallFolder` once the old one exits. A new version that throws in `Start` hands back to the exe set aside, through the same swap, so the old version is `LetsClip.exe` again; `AttemptedUpdate` keeps the background from trying that release again.
- A good start as the installed exe deletes every `LetsClip_v*.exe` beside it (`Updater.DeleteOtherVersions`) and every other unpacked folder under `%Temp%\.net\LetsClip` and the older `%Temp%\.net\LetsClip_v*` (`DeleteOldUnpackedVersions`), renaming each first so a copy still running keeps its own.
- Every Release start outside a sandbox rewrites, on a pool thread under one lock (`CaptureController.RegisterWithWindows`, which reads the setting inside the lock so quick toggles land in order): the Run value `"<exe>" --tray` while Start with Windows is on, the Start menu shortcut (`Programs\01 Apps` where that folder exists, the owner's machines, else `Programs`), the Desktop shortcut while it exists (made by an install from a download, never by an update or a takeover, which start with `--after-update`, and never brought back once deleted), the crash restart (`RegisterApplicationRestart`), and `HKCU\...\Uninstall\LetsClip`: name, version, publisher, icon, install folder, size (the exe plus what it unpacked), no modify or repair, `UninstallString` `"<exe>" --uninstall`. The Start with Windows switch used to write the shortcut on the window's thread, a 0.8 s freeze.
- `--uninstall` (`App.Uninstall`, `Updater.Uninstall`), what Settings, Apps runs after its own question: the running LetsClip is asked to exit and waited for up to a minute, the Run value, both shortcuts and the Uninstall entry go, the cache, thumbnails and logs go, a message says the clips stay and where; once it is closed, a hidden `cmd` deletes the install folder, the WebView2 profile and this run's unpacked files about 3 s after the exe ends. The clips, their originals and exports, the settings and every clip's details stay, so a reinstall finds them all. A sandbox skips the registry, shortcuts and install folder.
- Tested on the owner's real profile on 14 November 2026 with versions 2.0.97 and 2.0.98 started through `explorer.exe`, his Run value, shortcuts, settings, clip details and logs saved first: 2.0.97 from a download folder installed as `LetsClip.exe` and deleted the download, v2.0.10 and v2.0.9 beside it and v2.0.10's 432 MB unpacked folder; 2.0.98 started while 2.0.97 ran took over in place (2.0.97 set aside, asked to exit, then deleted); `--uninstall` left only the clips, their details and the settings, after the WebView2 profile was moved into the after-exit step (the exiting copy's browser still held it). His named clips were renamed to their names by the first start.
- The first real update through GitHub, on 14 November 2026: the owner's v2.0.9, restarted in the tray, saw v2.0.10 at once, began installing after 10 minutes hidden, downloaded it in 4.1 s and verified it, and v2.0.10 moved itself to `LetsClip.exe` and deleted the download, `LetsClip_v2.0.9.exe` and both old unpacked folders, then wrote the Run value, the shortcuts and the Uninstall entry; the installed exe's SHA-256 matched the release. That hop carried `--installed-from`, so it also made a Desktop shortcut as if freshly downloaded; since v2.0.11 a start with `--after-update` never counts as an install, so a deleted Desktop shortcut stays gone.
- The first update through the name swap, the same morning: v2.0.10 found v2.0.11, downloaded it in 5.4 s, renamed itself to `LetsClip_v2.0.10.exe` and the download to `LetsClip.exe`, and v2.0.11 started 2 s later, deleted the set aside exe and the old unpacked build, and kept the Run value, shortcuts and Apps entry on `LetsClip.exe`; What Changed then held the one commit between them. Right after a release GitHub answered .NET's request for `releases/latest` with the previous tag for about 2 minutes while curl already saw the new one, so a check in that window finds nothing and the next comes 6 hours later or when the window opens; restart a copy that should update after that.
- Test builds outside a sandbox install themselves like a release and take over a lower installed version: test with versions above the owner's, save his Run value, shortcuts, settings, clip details and logs first, and end with `--uninstall` before installing the real release, or it would refuse to replace the higher test version.

## Updates

- `Updater.CheckAsync` reads the `releases/latest` redirect without following it, no token. `Tray.KeepUpdatedAsync` checks at launch and every 6 hours, 5 minutes after a check without an answer, every time the window is shown, and **More (⋮) → Check for Updates** asks by hand. Every check logs the latest tag, or why it failed.
- A newer release goes to `DesktopShell.ReportUpdate`, which keeps the newest (`AvailableUpdate`) and raises `UpdatesChanged`: `UpdateDialog` (`LetsClip v2.0.10 is Out`) opens once per release per run (`TakeUnofferedUpdate`, also on the page's first render, so a release found in the tray is offered when the window opens), and a red dot stays on More until restart. A check by hand always opens it.
- The dialog lists What Changed: the titles of every commit from this build's to the release's tag (`Updater.ChangesAsync`, GitHub's compare API, newest first, at most 250), in `ChangeList`, the SoTF.Editor look. After an update, the first start that finds a new build's commit (`UserSettings.SeenCommit`, kept by Reset to Default) reads the commits since the last one and shows them once when the window opens (`ChangesDialog`, `Updated to v2.0.11`); an unreadable answer is asked again next start. Installs before v2.0.10 store no commit, so their first update shows nothing.
- Updates install themselves once the window has been hidden for 10 minutes with no export or save running (`Tray.InstallWhenIdleAsync`), the owner's pick: losing the unsaved replay to an update does not matter. Update Now runs the same `Tray.InstallUpdateAsync`, one install at a time, and hides the X and Escape until a failure. Its progress shows nothing until the first bytes arrive (`TransferProgress`, shared with the clips folder move), where it read `1 KB` before.
- `UserSettings.AttemptedUpdate` holds the tag of a launched update; the background skips that tag, Update Now still installs it, and a good start at or above it clears it.

## Signed Updates

- Each release's exe is signed with ECDSA P-256 over SHA-256 by a key that never leaves the owner's PC (`C:\Users\yusuf\.letsclip\update-signing.pem`, outside every repository, never committed, uploaded or printed; a copy is in his iCloud Drive). The signature, base64 of OpenSSL's DER form, is the release body. The public key is `Updater.SigningKey`.
- `Updater.DownloadAsync` checks GitHub's asset digest, then the signature (`IsSigned`, checked by `SelfTestPasses`). A mismatch throws `InvalidDataException`: Update Now says `The download could not be verified` and opens the release page, the background logs it and keeps recording. Every install from v2.0.4 on refuses an unsigned update.
- Signing, in Git Bash: `openssl dgst -sha256 -sign ~/.letsclip/update-signing.pem LetsClip_v<version>.exe | base64 -w0 > signature.txt`, then `gh release create v<version> <exe> --title "LetsClip v<version>" --notes-file signature.txt`. Check with `gh release view v<version> --json body -q .body` against the file.
- Losing the key: no new release can be signed and installs stay where they are. The way out is a release with a new public key that people download themselves.
